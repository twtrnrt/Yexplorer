文件管理器 —— 架构总览（V1）

技术栈：C++17 + Win32 API + Shell COM + ComCtl32  |  目标平台：Windows 10 / 11 x64  |  仓库：C:\git\explorer  |  更新：2026-11-14

一、项目定位与边界

做一个日常可用的 Windows 文件管理器，替代系统自带资源管理器的窗口部分。

要做的：
  • 独立 GUI 进程，双击启动；后续通过注册表接管「打开文件夹」动作
  • 底层用 IShellFolder 枚举，和资源管理器同源，支持此电脑 / 回收站 / 网络等虚拟文件夹
  • 原生控件：TreeView（目录树）、ListView（文件列表）、Toolbar、地址栏
  • 文件操作用 IFileOperation，复用系统原生进度、冲突弹窗、回收站、撤销
  • 原生右键菜单、OLE 拖拽、系统图标与缩略图
明确不做的：
  • 不替换 explorer.exe 进程本身。桌面、任务栏、开始菜单都由它提供， 强行替换属于不受支持的黑改方案，会丢任务栏和桌面，稳定性极差
  • 不做自定义美化（Mica、圆角、自绘主题）——样式不是本项目目标
  • V1 不做数据库索引（详见第五节）

二、技术选型与理由

维度选择理由
语言C++17操作 Shell COM 最顺手，生态案例最多；原生机器码，无 GC 停顿
界面Win32 + ComCtl32 原生控件交互行为与系统原生一致；不做自绘框架
目录枚举IShellFolder而非 FindFirstFile。这是能打开「此电脑/回收站/网络/压缩文件夹」的关键
文件列表ListView 虚拟模式 LVS_OWNERDATA不把所有条目塞进控件，按需回调填充，十万级文件不卡
文件操作IFileOperation系统原生引擎：进度条、冲突处理、回收站、撤销全都白拿
COM 生命周期Microsoft::WRL::ComPtrSDK 自带，零第三方依赖，自动 AddRef/Release，规避本项目最大风险点

第三方依赖（全部 header-only，MIT，产物仍是单 exe）

库用途状态

spdlog日志，开发期排查用待引入
MSVC AddressSanitizer越界 / UAF 检测（编译器开关，非第三方）待启用
明确不引入：Qt、wxWidgets（自绘或过重，与「贴近原生」冲突）、Boost（C++17 标准库已覆盖需求）。 WTL 暂缓，等骨架跑通后按需评估。

五、关于数据库：V1 不做，理由如下

曾考虑「把文件结构全部存数据库、软件从库里读」来加速。结论是不做：

  • 本地 SSD 场景不会更快。NTFS 与文件系统缓存本身已是内存级高速缓存， 多一层 SQLite 查询只是多一次 IO。目录读取的物理上限由磁盘决定，绕过内核没有收益。
  • 一致性是致命问题。别的程序（原生资源管理器、脚本）随时增删改文件， 数据库必须靠 ReadDirectoryChangesW 或定时扫描同步；SMB 网络盘大量不支持变更通知， 一旦失同步，列表会显示已删除的文件、看不到新文件——对文件管理器是不可接受的 bug。
  • 每次文件操作都要多写一次库，反而增加延迟。

真正有收益的只有一种场景：慢速远程大目录（NAS / SMB，几万条目）。 因此这个能力放到 V2，做成可选开关的离线索引模块，只对用户主动指定的网络目录生效， 默认关闭，绝不作为主数据源。

六、性能设计要点

  1. UI 线程永不做重活。目录枚举、图标读取全抛后台线程，带取消令牌； 切换目录时立即取消上一个枚举任务。
  2. 虚拟列表。ListView 强制 LVS_OWNERDATA，按需回调填充，不预载全部条目。
  3. 图标 LRU 缓存。避免重复调用 SHGetFileInfo。
  4. 第三方 Shell 扩展开关。这是最大的提速点——原生资源管理器卡顿， 多数是网盘、杀毒的外壳扩展拖的。给自己的程序加个「不加载第三方扩展」的开关。
  5. 缩略图延迟加载。只对可视区域拉取。
  6. 进程隔离的天然优势。我们是独立 exe，某个扩展或缩略图崩溃不会连带拖死整个界面。
性能预期要说清楚：不要期望「全方位比原生快很多」。 本地方向小目录，速度和原生持平（底层都是同一套内核）。 优势体现在大目录不卡死、网络盘响应更稳、不受第三方扩展拖累—— 赢在「流畅与不阻塞」，不是赢在磁盘 IO 带宽。
