## 坑 1：CVT1100 资源重复（MANIFEST 被嵌入两次）

**发生时间**：2026-11-14（阶段 0 骨架自检时）

**现象**：

```
CVTRES : fatal error CVT1100: 资源重复。类型: MANIFEST，名称: 1，语言: 0x0409
LINK : fatal error LNK1123: 转换到 COFF 期间失败: 文件无效或损坏
```

**原因**：

清单（manifest）被嵌入了两次：

1. `res/app.rc` 里手工写了 `1 RT_MANIFEST "app.manifest"`，编进 `app.res`；
2. `Explorer.vcxproj` 里又写了 `<Manifest Include="res\app.manifest" />`，
   加上默认 `GenerateManifest=true`，MSBuild 会额外生成一份
   `FileExplorer.exe.embed.manifest.res`。

链接时两个 `.res` 都带 MANIFEST 资源 → 重复。

**排查过程**：

看 `obj\x64\Debug\` 目录，发现同时存在：

```
app.res                              ← 我们的
FileExplorer.exe.embed.manifest.res  ← MSBuild 自动生成的
```

**踩的第二个坑（关键）**：

第一次修的时候，把 `<GenerateManifest>false</GenerateManifest>` 写在了
`ItemDefinitionGroup` 的 `Link` 元数据里，**没有生效**，编译依旧报同样的错。

原因是 `GenerateManifest` 是**项目级属性**，必须写在 `PropertyGroup`（Configuration 那一组）里，
写在 `Link` 的元数据里 MSBuild 根本不读。

**最终解法**：

1. 清单**只保留 `res/app.rc` 这一处来源**（好处：清单来源唯一，任何构建方式结果一致，
   以后即使直接用 cl.exe 单独编译也带清单）；
2. 在 `Explorer.vcxproj` 的两个 `PropertyGroup`（Debug|x64、Release|x64）里写
   `<GenerateManifest>false</GenerateManifest>`，关掉 MSBuild 自动清单生成；
3. 把 `<Manifest Include=...>` 改成 `<None Include=...>`，只让它在 VS 解决方案里可见，不参与构建。

**验证方式**：

用 mt.exe 从编译产物里提取清单，确认内容正确：

```powershell
& "C:\Program Files (x86)\Windows Kits\10\bin\10.0.26100.0\x64\mt.exe" `
   '-inputresource:C:\git\explorer\bin\x64\Debug\FileExplorer.exe;#1' `
   "-out:$env:TEMP\fe_extracted.manifest"
```

检查四项：Common-Controls v6、PerMonitorV2、longPathAware、Win10/11 supportedOS，
四项全部为 True 才算通过。

## 坑 2：`PCITEMIDLIST` 类型不存在（新版 SDK 已改名）

**发生时间**：2026-11-14（阶段 1 写 Shell 枚举时）

**现象**：

```
ShellFolder.cpp(53,51): error C2061: 语法错误: 标识符"PCITEMIDLIST"
ShellFolder.cpp(192,30): error C2660: "IsFolder": 函数不接受 2 个参数
```

（后面一堆连带错误，都是同一个根因引发的）

**原因**：

我沿用了老代码里的 `PCITEMIDLIST` 类型名。但查 SDK 头文件
`C:\Program Files (x86)\Windows Kits\10\Include\10.0.26100.0\um\shtypes.h` 发现：

- 第 167 行定义的是 **`LPCITEMIDLIST`**（`typedef const ITEMIDLIST __unaligned *LPCITEMIDLIST`）
- 文件里**没有 `PCITEMIDLIST` 这个 typedef**（只有 `PCIDLIST_ABSOLUTE`、`PCUITEMID_CHILD` 等宏别名）

也就是说新版 SDK 里 `PCITEMIDLIST` 已经不是有效类型名了。

**解决办法**：

把三处 `PCITEMIDLIST` 全部改成 **`LPCITEMIDLIST`**：

- `GetDisplayName(IShellFolder*, LPCITEMIDLIST)`
- `IsFolder(IShellFolder*, LPCITEMIDLIST)`
- `FillExtraInfo(IShellFolder*, LPCITEMIDLIST, ShellEntry&)`

调用处原本传的是 `LPITEMIDLIST`，可以隐式转成 `LPCITEMIDLIST`（加 const），无需改调用。

`IShellFolder::GetAttributesOf` 的第二个参数要求 `PCUITEMID_CHILD_ARRAY`，
它等价于 `LPCITEMIDLIST*`，所以函数内直接 `&childPidl` 就可以，不需要额外转换。

**经验**：

写 Win32/Shell 代码时，PIDL 相关类型有新旧两套名字（`PCITEMIDLIST` / `LPCITEMIDLIST`、
`PCUITEMID_CHILD` / `PCIDLIST_RELATIVE` 等）。**新代码统一用 `LPCITEMIDLIST` 家族**，
别抄老博客里的 `PCITEMIDLIST`。

## 坑 3：`ListView_*` 是宏，前面不能加 `::`

**发生时间**：2026-11-14（阶段 2 写列表控件时）

**现象**：一编译就出一大片莫名其妙的语法错误：

```
FileListView.cpp(73,7): error C2589: "(":"::"右边的非法标记
FileListView.cpp(73,7): error C2059: 语法错误:"("
FileListView.cpp(73,7): error C2143: 语法错误: 缺少";"(在"SendMessageW"的前面)
...
```

错误行号指向 `ListView_SetExtendedListViewStyle(...)`，看起来完全正常。

**原因**：

`ListView_SetExtendedListViewStyle`、`ListView_InsertColumn`、`ListView_SetColumnWidth`、
`ListView_SetItemCountEx`、`ListView_GetNextItem` 这些都是 **commctrl.h 里的宏**，
不是真正的函数。

我写了 `::ListView_SetColumnWidth(...)`，宏展开后变成：

```cpp
::(BOOL)SNDMSG((hwndLV), LVM_SETCOLUMNWIDTH, ...)
```

`::` 后面跟 `(BOOL)` 当然是非法语法。编译器报错位置落在宏展开后的 `SendMessageW` 上，
所以错误信息看起来完全不搭边。

**解决办法**：

去掉这些宏前面的 `::` 前缀：

```cpp
// 错误
::ListView_SetColumnWidth(m_hWnd, 0, width);

// 正确
ListView_SetColumnWidth(m_hWnd, 0, width);
```

**经验**：
Win32 里大量「函数」其实是宏（`ListView_*`、`TreeView_*`、`ListView_SetItemState` 等）。
判断方法：能对 `::` 用的一定是真函数；拿不准就别加 `::`。

## 坑 5：`HIMAGELIST` / `SHFILEINFOW` 未定义（头文件顺序）

**现象**：

```
ShellIcon.h(63): error C3646: "m_hImageList": 未知重写说明符
ShellIcon.cpp(31,5): error C2065: "SHFILEINFOW": 未声明的标识符
ShellIcon.cpp(88,20): error C2039: "SHGetImageList": 不是 "global namespace" 的成员
```

**原因**：

- `HIMAGELIST` 定义在 `commctrl.h`，不在 `windows.h`
- `SHFILEINFOW` / `SHGetFileInfoW` / `SHGFI_*` 定义在 `shellapi.h`
- `IImageList` / `SHGetImageList` 在 `commoncontrols.h`，而 `commoncontrols.h`
  本身依赖 `HIMAGELIST` 已定义

我一开始只写了 `windows.h` + `commoncontrols.h`，所以全崩。

**正确顺序**：

```cpp
#include <windows.h>
#include <commctrl.h>        // HIMAGELIST
#include <shellapi.h>        // SHGetFileInfoW / SHFILEINFOW / SHGFI_*
#include <commoncontrols.h>  // IImageList / SHGetImageList（必须放在前两个之后）
```

**经验**：Windows Shell 相关的头文件彼此有依赖，顺序错了就是一堆「未声明」。
先 `windows.h`，再 `commctrl.h`，再 `shellapi.h`，最后 `commoncontrols.h`。

## 坑 6：用 `C:\` 取文件夹图标，拿到的是硬盘图标

**发生时间**：2026-11-14（用户反馈「文件夹的图标样式不对」）

**现象**：列表里所有文件夹显示的都是「灰色硬盘 + 蓝色四格 + 绿灯」，不是黄色文件夹。

**原因**：

```cpp
// 错误写法
SHGetFileInfoW(L"C:\\", FILE_ATTRIBUTE_DIRECTORY, &sfi, sizeof(sfi),
               SHGFI_SYSICONINDEX | SHGFI_SMALLICON | SHGFI_USEFILEATTRIBUTES);
```

虽然带了 `SHGFI_USEFILEATTRIBUTES`（本意是「别去访问这个路径，只按属性算图标」），
但路径写成 `C:\` 这种盘符根目录，Shell 依然把它当成**驱动器**，返回的是硬盘图标。

探针实测对比：

| 样本 | 拿到的图标 |
|---|---|
| `"C:\"` + 目录属性 | 灰色硬盘（错） |
| `"folder"` + 目录属性 | 标准黄色文件夹（对） |

**解决办法**：样本用一个普通名字，不要用盘符路径。

```cpp
// 正确写法
SHGetFileInfoW(L"folder", FILE_ATTRIBUTE_DIRECTORY, &sfi, sizeof(sfi),
               SHGFI_SYSICONINDEX | SHGFI_SMALLICON | SHGFI_USEFILEATTRIBUTES);
```

**连带影响**：左侧导航栏「快速访问」的分组标题原本也走 `GetIconIndexByPath(L"C:\\")`
取图标，同样拿到硬盘图标。为此 `IconCache` 新增 `FolderIconIndex()`，
导航栏分组标题直接用它。

**经验**：`SHGetFileInfo` + `USEFILEATTRIBUTES` 的「样本」不要用带盘符的绝对路径，
用 `"folder"` / `"file.txt"` 这类普通名字最稳。

## 坑 7：系统标准按钮改不成 Windows 11 的扁平样子

**现象**：顶部后退/前进/向上三个按钮带灰色立体边框和内凹底，
和 Windows 11 资源管理器的「无边框、悬停才出现浅灰圆角」完全不是一个观感。

**原因**：`BUTTON` 类控件的外观由系统主题绘制，`BS_FLAT` 也只是去掉部分立体感，
无法做到真正的「平时完全透明」。

**解决办法**：自绘一个 `FlatButton`（`src/ui/FlatButton.*`）：

| 状态 | 画法 |
|---|---|
| 平时 | 只画箭头，背景留窗口底色 |
| 悬停 | `RGB(240,240,240)` 圆角 6px 背景 |
| 按下 | `RGB(219,219,219)` 圆角 6px 背景 |
| 禁用 | 箭头改用 `COLOR_GRAYTEXT` |

箭头不用图标字体（`Segoe MDL2 Assets` 在 100% 缩放下边缘会发毛），
直接用两三条 `MoveToEx`/`LineTo` 线段画，粗细角度可控。

点击时向父窗口发 `WM_COMMAND` + `BN_CLICKED`，和原来的按钮处理逻辑完全兼容。

> 后记（阶段 3.7）：用户反馈线段画的箭头观感不对，最终改回图标字体
> （`Segoe Fluent Icons`，没有则退回 `Segoe MDL2 Assets`），边框保持去掉。
> 教训：这类"像不像"的判断以用户实测为准，不要只按自己的审美拍板。

## 坑 8：同目录复制弹「目标文件夹和源文件夹相同」

**发生时间**：2026-11-14（阶段 4 文件操作）

**现象**：在同一目录里选中 `a`，`Ctrl+C` 再 `Ctrl+V`，
程序不生成副本，而是弹出一个确认框：

```
目标文件夹和源文件夹相同。
[取消]  [为所有当前项目执行此操作(&A)]
```

而且这个框如果不点，操作就一直卡在那里（自动化脚本因此卡死超时）。

**原因**：

用批量接口把项目"复制"到它自己所在的目录：

```cpp
operation->CopyItems(items, targetFolder);   // targetFolder 就是源所在目录
```

系统检测到目标 == 源，就询问用户要不要继续。
资源管理器不弹这个，因为它在同目录粘贴时是"复制并改名"，不走这条路径。

**解决办法**：先判断是不是同目录，是的话自己算好新名字逐个复制：

```cpp
if (AllSourcesInTargetDirectory(sourcePaths, targetDirectory))
{
    // 自己生成 "a - 副本" 这样的名字，逐个 CopyItem 并指定新名字
    operation->CopyItem(item, targetFolder, newName.c_str(), nullptr);
}
else
{
    // 正常情况：批量复制，一个进度框搞定
    operation->CopyItems(items, targetFolder);
}
```

新名字规则和资源管理器一致：

| 源 | 副本 |
|---|---|
| 文件夹 `a` | `a - 副本` |
| 文件 `fe.txt` | `fe - 副本.txt` |
| 已存在同名副本 | `a - 副本 (2)`、`a - 副本 (3)` … |

**另一个必须做的设置**：`IFileOperation::SetOwnerWindow(hwnd)`。
不设置的话，系统的进度框/确认框没有归属窗口，可能出现「看不见但一直等用户点」，
操作永远不结束。封装里统一传主窗口句柄。

## 坑 9：同步调用 IFileOperation 会把整个窗口冻住

**发生时间**：2026-11-14（阶段 5）

**现象**：复制 1GB 文件时，进度框能点「取消」，但主窗口点不动，
不能翻目录、不能切窗口，要等复制完才恢复。

**原因**：`PerformOperations()` 是同步的，调用期间界面线程一直卡在里面，
消息循环转不动。资源管理器不是这样，因为它内部是异步模型。

**解决办法**：把整个操作丢到一条后台线程去等。

```cpp
m_operationThread = std::thread([...]()
{
    // 后台线程必须自己初始化 COM，不能借用主线程的
    HRESULT initHr = ::CoInitializeEx(nullptr, COINIT_APARTMENTTHREADED);
    HRESULT result = operation();          // 这一步在这里慢慢等，界面不受影响
    if (SUCCEEDED(initHr)) ::CoUninitialize();
    ::PostMessageW(notifyWindow, WM_APP_OPERATION_DONE, (WPARAM)result, 0);
});
```

主窗口收到 `WM_APP_OPERATION_DONE` 后刷新列表，并根据返回的 HRESULT
判断成功/失败（失败含用户点取消）。

**几个细节**：

1. **同一时间只允许一个操作**——两个操作同时弹进度框会互相打架。
   用一个共享的 `std::atomic<bool>` 标记，主线程和后台线程都能安全读写。
2. **传给后台线程的数据要拷贝一份**（路径列表），不要让它直接读界面成员变量，
   否则可能和界面线程同时改同一块内存。
3. **窗口关闭时要 join 线程**，否则线程还在跑而窗口已经销毁，
   往已销毁的窗口 PostMessage 会失败（不会崩，但白跑）。
4. `PostMessage` 用 `static_cast<WPARAM>(hr)` 把 HRESULT 带回来，
   收到后 `static_cast<HRESULT>(static_cast<LONG_PTR>(wParam))` 还原。

**实测**：1GB 复制期间，每 120ms 往主窗口发一次探测消息，
每次都 1～20ms 返回；改造前同样探测会超时。

## 坑 10：刷新列表时整屏重建，选中和滚动位置全丢

**发生时间**：2026-11-14（阶段 6，用户反馈"删文件加文件时整个列表会刷新，感觉不太好"）

**现象**：删掉一个文件，列表不是"少一行"，而是整片闪一下，
滚动条跳回顶部、选中的东西也没了。

**原因**：三处叠加。

1. 操作完成后调 `RefreshCurrentFolder()`，整个目录重新枚举一遍再重建列表
2. `SetResult` 里调了 `LVM_SETITEMSTATE(-1, 0)` —— 这一句把**所有行的状态**清空（等于取消全部选中）
3. `InvalidateRect(hwnd, nullptr, TRUE)` —— 第三个参数 TRUE 表示"先把背景擦掉再重画"，整片闪白

**解决办法**：

**a) 能局部改的就别重扫**：删除和新建都有明确知道"少了哪几项 / 多了哪一项"，
直接在数据 vector 上增删，再 `ListView_SetItemCountEx` 新数量，只重画变化的区域。
删一个文件的开销从"重扫 100 项 ≈ 110ms"变成 0。

**b) 非要重扫的时候，把用户状态还回去**：
```cpp
// 刷新前：记下选中项的名字 + 顶部那一行是谁
// 刷新后：按名字找回对应的行，重新选中 / 重新滚到那个位置
```
为什么记「名字」而不是记「行号」：增删之后行号会整体错位，名字不会。

**c) `InvalidateRect` 第三个参数改 FALSE**：不擦背景，控件自己画背景，就不会闪白。

**d) 去掉 `LVM_SETITEMSTATE(-1, 0)`**：这一句是"清空所有状态"，正常刷新不需要它。

**教训**：虚拟列表的"刷新"不等于"重建"。数据在我们手里，
能算出差异就只动差异部分；算不出差异时也要把用户看到的状态（选中、滚动）手工还原。

## 坑 11：虚拟列表里做原地改名，控件不知道内容

**发生时间**：2026-11-14（阶段 6，F2 重命名）

**现象**：加了 `LVS_EDITLABELS` 之后按 F2，编辑框弹出来但里面是空的。

**原因**：虚拟模式下控件内部不存任何一行文本，它没法自己填编辑框的初始内容。

**解决办法**：在 `LVN_BEGINLABELEDIT` 里主动把名字塞进去：

```cpp
case LVN_BEGINLABELEDIT:
{
    NMLVDISPINFOW* info = reinterpret_cast<NMLVDISPINFOW*>(lParam);
    info->item.mask |= LVIF_TEXT;
    info->item.pszText = const_cast<wchar_t*>(m_result->entries[index].name.c_str());
    return FALSE;   // 返回 FALSE 才允许编辑（返回 TRUE = 拒绝）
}
```

改名结束时 `LVN_ENDLABELEDIT` 的 `item.pszText` 就是用户输入的新名字；
如果用户按 Esc 取消，`pszText` 是 nullptr，此时什么都不要做。

**注意**：`pszText` 指向的字符串要在整个编辑过程中有效，
所以直接指向 vector 里的 `std::wstring` 是安全的（编辑期间不会刷新列表）。

## 坑 12：剪贴板内存释放时机（一错就崩）

**发生时间**：2026-11-14（阶段 7，剪贴板互通）

三个必须记住的点：

1. **`SetClipboardData` 成功 = 内存归系统了。**
   ```cpp
   if (::SetClipboardData(CF_HDROP, hDrop) == nullptr)
   {
       ::GlobalFree(hDrop);      // 只有失败时才是我们的，要自己释放
   }
   // 成功路径上绝对不能再 GlobalFree，否则程序直接崩
   ```
2. **`GetClipboardData` 的内存只在 `CloseClipboard` 之前有效。**
   所有字符串必须在关闭剪贴板前 `wcscpy` 或 `DragQueryFileW` 复制出来。
3. **剪贴板是独占的。** `OpenClipboard` 失败说明被别的程序占着，
   要重试（我们重试 10 次、每次 50ms），不要直接放弃。

另外：`CF_HDROP` 的内存布局是 `DROPFILES` 头 + 一串 UTF-16 路径，
**每条路径以 `\0` 结尾，整个列表最后再补一个 `\0`**。少这一个字节，
接收方（比如资源管理器）就读不到最后一条。

`Preferred DropEffect` 这个格式是按**字符串名字**注册的：
`RegisterClipboardFormatW(L"Preferred DropEffect")`，
不能自己编一个常量，必须和系统/资源管理器写的名字一模一样，否则读不到。

## 坑 13：`IImageList::Add` 加图标加不进去

**发生时间**：2026-11-14（阶段 8，剪切项图标变淡）

**现象**：想往 `ImageList` 里追加一个"淡化版"图标，
调 `pImageList->Add(hIcon, nullptr, &index)` 编译却报参数不匹配。

**原因**：`IImageList` 有两个重载：

```cpp
HRESULT Add(HBITMAP hbmImage, HBITMAP hbmMask, int* pi);            // 位图版（3 个参数）
HRESULT Add(HBITMAP hbmImage, HBITMAP hbmMask, COLORREF crMask, int* pi);  // 带掩码色版
```

它是给**位图**用的，没有收 `HICON` 的重载。用位图版硬塞 HICON 也不对。

**解决办法**：改用 comctl32 的 `ImageList_ReplaceIcon`，它的 `-1` 表示"追加到末尾"：

```cpp
int newIndex = ::ImageList_ReplaceIcon(m_imageList, -1, hIcon);
// 用完把临时 HICON 销毁（ImageList 已经复制了一份）
::DestroyIcon(hIcon);
```

**经验**：`IImageList` 和 `ImageList_*` 系列函数这两套 API 的语义不完全通用，
遇到"类型不对"先翻两边的声明，别硬转指针。

## 坑 14：`DROPEFFECT` 在这个工程里没有类型，只有常量

**发生时间**：2026-11-14（拖放，编译报"未定义标识符 DROPEFFECT"）

另外头文件里补 `#include <ole2.h>`（`IDropTarget` / `IDataObject` / `DoDragDrop` 都在这）。

## 坑 15：`IDropTarget` 回调给的点是「屏幕坐标」，不是客户区坐标

**发生时间**：2026-11-14（拖放，左栏怎么都收不到拖放）

**现象**：往列表里拖能落地，往左栏树上拖永远没反应，光标也不变。
日志里 `DragEnter` 收到了，但算出来的落点目录是空的。

**原因**：`IDropTarget::DragEnter / DragOver / Drop` 传进来的 `POINTL pt` 是
**屏幕坐标**（OLE 拖动循环全程用屏幕坐标）。原先直接当客户区坐标用，
`TreeView_HitTest` 拿到一个远超控件范围的 y，自然什么都没有。

列表那边之所以"碰巧正常"，是因为主窗口正好摆在屏幕 (0,0)，
屏幕坐标和客户区坐标数值上重合了——这种"碰巧对"最坑，换台机器就错。

**解决办法**：在计算落点前先 `ScreenToClient`：

```cpp
POINT client = { pt.x, pt.y };
::ScreenToClient(m_hwnd, &client);   // m_hwnd 是注册拖放的那个窗口（列表或树）
```

**经验**：OLE 拖放的坐标一律按屏幕坐标理解，谁接待谁负责转换。

## 坑 16：左栏节点命中要认「整行」，不能只认文字区

**发生时间**：2026-11-14（同上，修完坐标还是收不到）

**现象**：坐标修正后，点在节点**文字上**能放，点在文字右侧的空白处还是不行。

**原因**：`TVHITTESTINFO::flags` 的取值很细：

| flags | 含义 |
|---|---|
| `TVHT_ONITEMICON` | 图标上 |
| `TVHT_ONITEMLABEL` | 文字上 |
| `TVHT_ONITEMRIGHT` | **同一行文字右边的空白** |
| `TVHT_ONITEMBUTTON` | 左侧展开按钮 `+` |
| `TVHT_ONITEM` | 前三个的合集 |

原来只放行 `ONITEMLABEL | ONITEMICON | ONITEM | ONITEMBUTTON`，
点在文字右侧拿到的是 `TVHT_ONITEMRIGHT`，被挡掉了。

**解决办法**：只把"纯展开按钮"排除，其它整行都接受：

```cpp
if (hitItem == nullptr) return L"";
if ((flags & TVHT_ONITEMBUTTON) != 0 &&
    (flags & (TVHT_ONITEMLABEL | TVHT_ONITEMICON | TVHT_ONITEMRIGHT)) == 0)
{
    return L"";   // 只点在 "+" 上，不算
}
```

配合 `TVS_FULLROWSELECT`，体验才和资源管理器左栏一致（整行高亮、整行能放）。

## 坑 17：拖放结束后，数据对象不能立刻销毁

**发生时间**：2026-11-14（拖放）

**现象**：`DoDragDrop` 返回"拖放成功、效果=复制"，
但目标目录里什么都没有。同一份代码拖成"移动"却是好的。

**原因**：部分目标（资源管理器最典型）在 `Drop` 返回之后，
还会在后台线程继续从 `IDataObject` 读数据来做实际的文件操作。
我们的 `wil::com_ptr` 在 `DoDragFiles` 退出时就归零销毁了，
目标再去 `GetData` 就是访问已释放对象，操作静默失败。

**解决办法**：把刚用过的数据对象**延迟释放**，保留最近几次：

```cpp
// 拖完不销毁，先存起来，留 4 个再滚动丢弃
g_recentDataObjects.push_back(dataObject);
while (g_recentDataObjects.size() > 4)
{
    g_recentDataObjects.erase(g_recentDataObjects.begin());
}
```

标准壳数据对象（见坑 18）额外持有 PIDL，所以有对应的
`g_recentShellObjects` 一起延迟释放。

**经验**：凡是"我把东西交给别的进程、它可能异步用"的场景，
生命周期都要按对方最慢的节奏算，不能按自己函数退出的时机算。

## 坑 18：只给 `CF_HDROP` 的数据对象，会让某些目标"成功了但什么都不做"

**发生时间**：2026-11-14（拖放，往资源管理器拖复制）

**现象**：`DoDragDrop` 返回 `DRAGDROP_S_DROP`、效果 `DROPEFFECT_COPY`，
资源管理器窗口里甚至出现了一下新文件的影子，但磁盘上始终没有文件。
换成往左栏拖（我们自己的放置目标处理）就一切正常。

**原因**：我们手搓的 `IDataObject` 只提供 `CF_HDROP`。
资源管理器内部处理"复制"时走的路径需要 **`Shell IDList Array`**（ID 列表格式），
拿不到就当作"这个源给不出项目"，于是什么也不做（返回效果却照常）。
而"移动"是另一条代码路径，恰好认 `CF_HDROP`，所以移动看起来是好的。

**解决办法**：不要自己拼数据对象，直接让系统造**标准壳数据对象**——
资源管理器自己往外拖用的就是它：

```cpp
// 1) 路径 → 绝对 PIDL
PIDLIST_ABSOLUTE full = ::ILCreateFromPathW(path.c_str());
// 2) 父目录 PIDL（去掉最后一项）
PIDLIST_ABSOLUTE parent = ::ILClone(full);
::ILRemoveLastID(parent);
// 3) 每项的相对 PIDL
children.push_back(::ILFindLastID(full));
// 4) 交给系统造
::SHCreateDataObject(parentPidl, cidl, childPtrs.data(), nullptr, IID_PPV_ARGS(&object));
```

几个必须注意的点：

1. **所有项必须在同一个父目录下**，`SHCreateDataObject` 只接受一组同父的相对 PIDL。
   跨目录多选时它造不出来，我们退回自己那个 `CF_HDROP` 简易对象（够用）。
2. **PIDL 要活到数据对象销毁**。`SHCreateDataObject` 不保证会克隆，
   所以我们把申请过的 PIDL 全部放进一个持有结构，析构时统一 `ILFree`。
3. `SHCreateDataObject` 的参数类型是 `PCUITEMID_CHILD_ARRAY`
   （`const ITEMIDLIST* const*`），直接传 `std::vector<PIDLIST_RELATIVE>::data()` 会
   报"转换丢失限定符"，要先转成 `std::vector<PCUITEMID_CHILD>` 再取 `.data()`。

**经验**：和外壳打交道，"看起来能用"不等于"目标真的会执行"。
数据格式齐全比代码简洁重要，能用系统提供的标准实现就别自己拼。

## 坑 19：`DoDragDrop` 的 allowed 里塞 `DROPEFFECT_LINK`，会改变别人的默认效果

**发生时间**：2026-11-14（拖放，Alt 拖动建快捷方式）

**现象**：为了让"Alt 拖动建快捷方式"生效，把
`DoDragFiles(..., allowed = COPY | MOVE | LINK)`。
结果拖出到资源管理器时，即使不按任何修饰键，对方也把效果判成"复制"，
而不是同盘默认的"移动"。

**原因**：目标在决定默认效果时会参考源声明的 allowed 集合；
出现 `LINK` 时它的判定会变得保守（按复制处理）。

**解决办法**：对外（给别的程序看）仍然只声明 `COPY | MOVE`，和资源管理器一致；
"Alt 建快捷方式"只在本程序内部生效——我们自己的放置目标
不再对效果做 `wanted & allowed` 的交集，而是直接用算出来的结果：

```cpp
// 我们自己的目标知道自己支持什么，不需要被 allowed 挡
*effect = ComputeDropEffect(keyState, m_sourcePreferredEffect, sameDrive(...));
```

代价：把文件从本程序 Alt 拖到**别的程序**窗口时，对方会显示"不允许"。
这符合资源管理器的行为（它对第三方目标也不承诺 LINK），可以接受。

## 坑 20：枚举开始时无脑清空列表 → 闪空 + 选中丢失

**发生时间**：2026-11-14（阶段 8，统一"不整表刷新"）

**现象**：每次刷新目录，列表先变成空的，再填回来；
刷新后选中项和滚动位置都没了，用户看起来像"整表重建"。

**原因**：`StartEnumeration` 里无条件 `SetResult(nullptr)` 清空数据。
后台枚举几十毫秒后回来再填，中间这段就是白屏空列表；
选中信息在被清空时就丢了，后面也没有东西可以还原。

**解决办法**：

1. **只有"目标目录 ≠ 当前显示目录"时才清空**。
   同一目录的刷新（F5、操作完成）保留旧数据，等新结果回来再用 `MergeResult` 做差异更新。
2. `MergeResult` 逐行比对 `fullPath` 找第一个不同处，
   全等就直接返回不重绘；不同则 `SetItemCountEx` + 还原选中/滚动 +
   `ListView_RedrawItems(第一个不同处, 末尾)`，只重画变化的那几行。
3. 还原选中前必须先 `LVM_SETITEMSTATE(-1, 0)` 清空全部选中，
   否则"选中的行号"会粘到新内容上（内容换了，行号没换，等于选错了东西）。

**经验**：性能问题的表层是"重绘太多"，里层往往是"数据先被丢掉、再重建"。
先保住数据，再谈只重绘哪里。

## 坑 21：`ReadDirectoryChangesW` 是阻塞的，不主动打断就关不掉

**发生时间**：2026-11-14（阶段 9.5，目录自动刷新）

**现象**：准备加"目录有变化就自动刷新"时，第一版想直接在界面线程里
`ReadDirectoryChangesW` 循环等。结果这条调用没有变化时**永远不返回**，
界面直接冻死。改成后台线程后，关窗口时又卡在 `join()` 上——线程还在等变化。

**解决办法**：

1. 监视放在独立线程，界面线程只负责收消息。
2. 停止时**必须先 `CancelIoEx(m_dirHandle, nullptr)`** 再 `join()`，
   否则 `ReadDirectoryChangesW` 一直阻塞，`join` 永不返回。
3. 单独一个 `HANDLE` 停止事件，`Stop()` 里先 `SetEvent` 再 `CancelIoEx`，
   两件事都要做：前者防止下一轮重新进入，后者打断当前正在等的那一次。

**经验**：凡是"同步等待型"的系统 API（`ReadDirectoryChangesW`、
`WaitForMultipleObjects`、`GetMessage`），都要同时准备好"取消路径"，
不然关闭时一定卡。

## 坑 22：自己程序的操作也会触发监视，不防抖会把界面刷成幻灯片

**发生时间**：2026-11-14（同上）

**现象**：粘贴 100 个文件时，监视每秒发几十条通知，
每条都触发一次刷新，界面疯狂闪、CPU 飙高。

**解决办法**：

1. 收到通知**不立刻刷新**，只 `SetTimer(id, 250ms)`。
   同一个定时器反复设置会不断重置，等于"等动静停下来再说"。
2. 定时器真正触发时才枚举一次，并走 `MergeResult` 差异更新。
3. 定时器里再挡两件事：**有文件操作正在跑**就跳过（操作结束会自己刷）、
   **正在 F2 改名**就跳过（否则编辑框被冲掉）。

**经验**：文件监视的通知是"事件流"，不能每个事件都干活，
要先合并成"一次状态变化"，再刷新一次。

## 坑 23：F2 改名的编辑框会被"自动刷新"冲掉

## 坑 24：拖进列表时"落点命中"要按行算，而且只认文件夹

**发生时间**：2026-11-14（阶段 9.5，拖到子文件夹）

**现象**：从资源管理器把文件拖到列表里某个文件夹图标上，文件没进那个文件夹，
而是进了当前目录——用户的原话是"拖到新建文件夹上没反应"。

**原因**：`ResolveTargetDirectory` 一律返回"当前目录"，
根本没做行命中测试。

**解决办法**：

1. `ListView_HitTest` 拿到行号，`row >= 0` 就算压在这一行上
   （列表开了整行选中，压在其他列上也应该认）。
2. 只把**文件夹行**当落点；压在文件行上按"没命中"处理，退回当前目录
   （否则会出现"把它自己放进它自己"这种怪事）。
3. 命中后返回该行的 `fullPath` 作为目标目录，
   后面的同盘/跨盘判断、效果计算全都基于**这个**目标，不是当前目录。
4. 视觉反馈用系统自带的 `LVIS_DROPHILITED`
   （先 `ListView_SetItemState(hwnd, -1, 0, LVIS_DROPHILITED)` 清全部，再给命中行设上）。
   路径没变就直接 return，别在每次 `DragOver` 都全表扫一遍。

**经验**：拖放的"落点"和"当前目录"是两个概念，
凡是列表类的放置目标都要实现行命中，否则等于把资源管理器最常用的一种操作弄丢了。

## 坑 25：`SHGetFileInfo` 用字符串查 `::{GUID}`，图标永远取不到

主文件夹、控制面板、回收站、网络、此电脑、桌面、库这些系统项，路径形如
`::{F874310E-B6B7-47DC-BC84-B9E6B38F5903}`。用

```cpp
SHGetFileInfoW(path.c_str(), 0, &sfi, sizeof(sfi), SHGFI_SYSICONINDEX | SHGFI_SMALLICON)
```

**正确做法**：先换 PIDL，再用 PIDL 查。

```cpp
PIDLIST_ABSOLUTE pidl = nullptr;
if (SUCCEEDED(SHParseDisplayName(path.c_str(), nullptr, &pidl, 0, nullptr))) {
    SHFILEINFOW sfi{};
    SHGetFileInfoW(reinterpret_cast<LPCWSTR>(pidl), 0, &sfi, sizeof(sfi),
                   SHGFI_PIDL | SHGFI_SYSICONINDEX | SHGFI_SMALLICON);
    // sfi.iIcon 就是系统小图标列表里的下标
    CoTaskMemFree(pidl);
}
```

| 主文件夹 | `::{F874310E-B6B7-47DC-BC84-B9E6B38F5903}` | 72 |
| 控制面板 | `::{21EC2020-3AEA-1069-A2DD-08002B30309D}` | 21 |
| 回收站 | `::{645FF040-5081-101B-9F08-00AA002F954E}` | 32 |
| 网络 | `::{F02C1A0D-BE21-4350-88B0-7367FC96EF3C}` | 17 |
| 此电脑 | `::{20D04FE0-3AEA-1069-A2D8-08002B30309D}` | 15 |
| 桌面 | `::{B4BFCC3A-DB2C-424C-B029-7FE99A87C641}` | 74 |
| 库 | `::{031E4825-7B94-4DC3-B131-E946B44C8DD5}` | 295 |

**注意**：`::{6D809377-6AF0-444B-8957-A3773F02200E}`（用户文件夹的另一个 CLSID）
用 `SHParseDisplayName` 解析会失败（`0x80070057` 参数错误）——遇到解析失败要能退回旧逻辑，不要崩。

## 坑 26：控制面板里的项"属性上是文件夹"，双击进去只有一个空层

控制面板（`::{26EE0668-A00A-44D7-9371-BEB064C98683}`）下面 9 个分类、
「所有控制面板项」（`::{26EE0668-...}\0`）下面 39 个项，`GetAttributesOf` 里
**23 个都带 `SFGAO_FOLDER`**。程序按"是文件夹就导航进去"，结果：
BitLocker、恢复、安全和维护、凭据管理器、电源选项…… 双击后只有一个空列表，
用户看到的正是"只有文件夹、打不开设置"。

**属性位分不出真文件夹和 applet**（实测）：

| 项 | 系统行为 | SFGAO |
|---|---|---|
| 字体 | 导航 | 0x00000000（连 FOLDER 都没有） |
| Windows 工具 | 导航 | 0x20000004（FOLDER，无 BROWSABLE） |
| BitLocker | 弹 applet | 0x28000004（FOLDER+LINK，无 BROWSABLE） |
| 恢复 / 安全和维护 / 凭据管理器 | 弹 applet | 0xA0000004（FOLDER+BROWSABLE） |
| 设备和打印机 | 导航（22 项） | 0xA0040004（多了 LINK） |
| 鼠标 / 键盘 / 声音 | 弹 applet | 0x00000004（只有 HASPROPSHEET） |

`BROWSABLE` 有、没有都不能区分，所以**别在这条路上继续试**。

**能用的判据：能不能真的枚举出子项。**

```
SHCreateItemFromParsingName → IShellItem
  → BindToHandler(BHID_SFObject, IID_IShellFolder)
  → EnumObjects(SHCONTF_FOLDERS | SHCONTF_NONFOLDERS)
```

拿到枚举接口 + 枚举出 ≥1 项 = 真容器（导航进去）；
枚举出 0 项 = 大概率是 applet（交给系统按默认动词打开）。
文件系统目录直接算容器，不用探测。

**但是**：第一版判据是"只要能拿到枚举接口就算容器"，结果**空回收站被误判成 applet**，
双击回收站直接弹系统窗口。所以"能拿到接口"不够，必须看**枚举结果里有没有项**，
再给"可能为空但确实是容器"的项（回收站）留一个白名单。

## 坑 27：顶层命名空间项的"父项"是物理桌面目录，不是「桌面」容器

回收站、控制面板、网络、主文件夹这些顶层项的 `IShellItem::GetParent()`
返回的是 **`C:\Users\kf168\Desktop`**（物理桌面目录，33 项），
而不是资源管理器里那个装着「此电脑/主文件夹/音乐/下载/桌面/网络…」的
「桌面」容器（51 项）。于是点"向上"会掉进一个"只有桌面文件"的列表，看起来像导航错了。

**修法**：拿 `SHGetKnownFolderPath(FOLDERID_Desktop)` 把物理桌面路径缓存一份，
`GetParentPath()` 里一旦算出这个路径，就换成顶层容器的伪路径 `::TopDesktop`。

判等要忽略大小写和末尾反斜杠，`_wcsicmp` 前先 `pop_back` 掉尾部 `\`。

## 自动化验证的限制（不是代码坑，但每次验收都会撞上）

**1. 程序化抢前台一律失败**

`SetForegroundWindow` / `AttachThreadInput` / `UI Automation SetFocus` 在这台机器上
都会失败（返回 false 或抛「目标元素无法接收焦点」）。所以：

- 真实鼠标点击会落到遮挡它的窗口上，点不到我们的控件
- `SendKeys` 真实键盘输入无处可去

**可用的替代手段**：

| 目的 | 手段 |
|---|---|
| 模拟双击列表项 | `PostMessage` 向 `SysListView32` 依次投 DOWN / UP / DBLCLK / UP |
| 点击按钮 | `SendMessage(主窗口, WM_COMMAND, MAKEWPARAM(id, BN_CLICKED), 按钮句柄)` |
| 截图 | `PrintWindow`（不依赖前台，照样能抓） |
| 找控件句柄 | `EnumWindows` + `EnumChildWindows` 枚举类名，**不要用 `FindWindowEx` 猜** |

**2. 跨进程 `SetWindowText` 不可靠**

对另一个进程的 Edit 调 `SetWindowText`，本进程读回来的 `GetWindowText` 是自己刚写进去的值，
但目标进程内的真实文本没变（UI Automation 读到的 `Current.Name` 才是真值）。
**结论：改别人程序的控件文本，必须用 UI Automation 的 ValuePattern，不能靠 SetWindowText。**

**3. 控件句柄别猜**

`Get-Process` 的 `MainWindowHandle` 在某些时刻会返回 0 或旧值；
`FindWindow("类名")` 也可能失败。用 `EnumWindows` 按进程 ID 筛，最稳。

**4. 注入的鼠标事件会被"最前面的那个窗口"吃掉**

用 `SetCursorPos` + `mouse_event` 注入真实鼠标时，事件落在**屏幕最上面那个窗口**，
不管我们要测的窗口在哪。豆包客户端、之前开着的资源管理器窗口都会把点击挡掉，
表现为"点了没反应、选中行一直是 -1、日志一条没有"——看起来像程序坏了，其实没点到。

对策：

- 测之前把被测窗口 `SetWindowPos(hwnd, HWND_TOPMOST, ...)` 临时置顶，测完再还原；
- 把不相关的资源管理器窗口先关掉，别让它压在列表区域；
- **先验证"能不能点中"**：点完立刻用 `LVM_GETNEXTITEM(0x100C, -1, LVNI_SELECTED=2)`
  查选中行，返回 0 才算点到了，再往下测。别跳过这一步。

**5. 拖动卡在循环里，会吃掉后面所有输入**

`DoDragDrop` 内部跑自己的模态循环。如果某次拖放没正常结束
（目标那边处理异常、或松手事件没送达），进程会一直停在拖动状态：
日志不再出现"拖出结束"，后续所有点击、拖动脚本全部无效。

**判断方法**：日志最后一条是"拖入进入"却没有对应的"拖出结束"。

**对策**：`Stop-Process -Name FileExplorer -Force` 重启再用，不要接着点。

**6. 落点压在文件夹图标上，文件会"消失"到那个文件夹里**

往资源管理器拖文件，如果松手位置正好压在某个**文件夹项**上，
文件会被放进那个文件夹（这是 Windows 正常行为）。
检查"没落地"之前，先确认落点是不是空白区——否则很容易误判成拖放失败。
本轮就出现过"以为复制失败，其实文件在 `桌面\测试pdf\` 里"。

**7. 想在"拖动进行中"截图，Add-Type 里写 `System.Drawing` 会编译失败**

`Add-Type -TypeDefinition` 里直接 `new System.Drawing.Bitmap` 会报
`CS1069 未能在命名空间 System.Drawing 中找到类型名 Bitmap`（类型已转发到
`System.Drawing.Common`），脚本直接中断，拖动还卡在半路。

对策：拆成三次调用，靠系统里全局的鼠标按键状态串起来——
①注入"按下 + 移动到目标"→ ②PowerShell 原生 `CopyFromScreen` 截图
→ ③注入"松开"。三段各自独立执行，中间不要用 C# 代码截图。

**8. 伪造 `LVM_SETITEMSTATE` + `WM_COMMAND 3201` 会把程序打崩**

想省掉鼠标、直接用消息让程序"打开第 N 项"，走的是：

```
SelectIndex(0)  →  LVM_SETITEMSTATE(0x102B) 改选中
PostMessage(main, WM_COMMAND, 3201, 0)       →  右键菜单的"打开"
```

结果：`LVM_GETSELECTEDCOUNT` 一直返回 0（虚拟列表的选择状态归程序自己的 `m_selection` 管，
外部硬改控件状态程序不认），紧接着 `WM_COMMAND 3201` 触发 **APPCRASH**
（`COMCTL32.dll`，`0xc0000005` / `0xc000041d`），三次里崩了两次。

**结论：这条路不要再用。** 要验证"打开某项"，老老实实注入鼠标双击。

**9. `GetForegroundWindow()` 返回 0 的时候，鼠标注入全部落空**

`fg=0[]` 表示系统当前没有前台窗口（切了虚拟桌面 / 息屏 / 锁屏）。
这种状态下 `SetCursorPos` + `mouse_event` 发出的点击**一个都到不了被测窗口**，
日志和标题完全不动，很容易误判成"程序坏了"。此时连点三次也不会有反应。

对策：注入前先取 `GetForegroundWindow()`，是 0 就直接判"环境不可用"，别继续测，
更别据此去改代码——上一轮就有过一次"以为改动失败、其实是测不进去，然后越改越坏"。

## 坑 28：控制面板 applet 的解析名，Shell 自己解析不回来

控制面板里「字体」「恢复」「设备管理器」「颜色管理」这些项的路径长这样：

```
::{26EE0668-A00A-44D7-9371-BEB064C98683}\0\字体
```

末尾是**显示名**，不是 GUID。实测：

| 路径 | Shell.Application.NameSpace | SHCreateItemFromParsingName |
|------|------|------|
| `::{26EE0668-…}\0`（所有控制面板项本身） | 成功，40 项 | 成功 |
| `::{26EE0668-…}\0\字体` | **返回 null** | **失败** |
| `::{26EE0668-…}\0\恢复` | **返回 null** | **失败** |
| `::{26EE0668-…}\0\设备管理器` | **返回 null** | **失败** |

结论：**凡是要打开这种项，都不能靠字符串重新解析**。
资源管理器能打开，是因为它手里一直握着枚举出来的 PIDL。

正确做法：枚举时把 `ILCombine(父绝对PIDL, 子PIDL)` 的结果按字节拷进数据快照
（PIDL 内部只有偏移量、没有指针，可以安全跨线程搬），打开时再还原成指针。

## 坑 29：用 IContextMenu 打开 applet 会回 E_INVALIDARG

拿到正确的 PIDL 之后，走 `IShellItem → BindToHandler(BHID_SFUIObject) → IContextMenu`：

| 步骤 | 结果 |
|------|------|
| `SHCreateItemFromIDList` | 成功 |
| `QueryContextMenu` | 成功，返回 45 项 |
| `InvokeCommand(lpVerb="open", fMask=CMIC_MASK_UNICODE\|NO_UI)` | **E_INVALIDARG (0x80070057)** |
| `InvokeCommand(MAKEINTRESOURCEA(0), fMask=NO_UI)`（第一项） | **E_INVALIDARG** |

同一套参数在别的项上没问题，说明是部分 cpl 外壳扩展不认这套结构。
最终改用 **`ShellExecuteExW` + `SEE_MASK_IDLIST | SEE_MASK_INVOKEIDLIST`**，一次成功。

补充：`WIN32_LEAN_AND_MEAN` 下 `SHELLEXECUTEINFOW` / `ShellExecuteExW` 在
`ShellFolder.cpp` 里找不到，需要显式 `#include <shellapi.h>`；`SEE_MASK_*`
和 `CMIC_MASK_*` 这些宏名仍然编不过，继续用字面值。

## 坑 30：截图目测的行坐标不可靠，别据此判断"点击错位"

排查「点第 14 行却进了第 17 行」时，按截图目测算出行首 y≈92、行高 22，

结论：列表行坐标不要从截图上量，**用两次已知命中反解**（点两个不同的 y，
看实际进了哪一项，代入 `y = y0 + h*index` 解方程）最可靠。

## 坑 31：虚拟列表用不了系统的分组视图

`LVM_ENABLEGROUPVIEW` / `LVM_INSERTGROUP` / `LVM_SETITEMGROUPID` 这套原生分组，
在 `LVS_OWNERDATA`（虚拟模式）下不生效——虚拟列表的行不由控件持有，
分组也没法挂到行上。

所以「此电脑」的「设备和驱动器」只能用方案 A 实现：
**在数据最前面插一行假标题，再由 `NM_CUSTOMDRAW` 把这一行自己画成标题**。
连带要处理的地方（漏一个就出问题）：

| 位置 | 要做的事 |
|------|----------|
| `LVN_GETDISPINFO` | 标题行不给图标（`I_IMAGENONE`），其余列留空 |
| `NM_CUSTOMDRAW` | 整行自绘（白底 + 灰字），返回 `CDRF_SKIPDEFAULT` |
| `LVN_ITEMCHANGING` | 拒绝标题行被选中，否则 Ctrl+A 会把它选中 |
| `LVN_BEGINLABELEDIT` | 拒绝标题行改名 |
| 标题 / 状态栏计数 | 要把标题行减掉，否则「6 项」变「7 项」 |
| 排序（`std::sort`） | 跳开标题行排，否则它会被排到中间，分组就散 |
| 列的排序开关 | 分组目录里干脆不响应排序（系统此电脑也不让排） |
## 坑 32：系统项取图标必须用枚举时留下的绝对 PIDL，不能靠解析名字符串

现象：控制面板「所有控制面板项」里一堆项没有图标（空白），有些能进但没有图标。

原因：这些项的解析名是 `::{26EE0668-…}\0\显示名`（父解析名后面接一个显示名子项），
`SHParseDisplayName` 对这种字符串一律失败，于是 `SHGetFileInfo` 拿不到东西、返回 0。

修法：枚举时本来就已经用 `SHGetIDListFromObject` + `ILCombine` 拿到了每项的绝对 PIDL
（当初是为了双击打开用的），直接把它再喂给 `SHGetFileInfoW`（`SHGFI_PIDL`）就能取到图标。
`FileListView::IconIndexForEntry` 现在第一步就走 PIDL，PIDL 拿不到才走原来的路径/扩展名兜底。
实测：37 项控制面板项的图标全部正常。

## 坑 33：「能不能进去」的判据要和我们自己的枚举器一致

现象：双击「存储空间」不打开设置面板，而是导航进去变成一个空列表。

原因：`ShellItemIsContainer` 原来先用 `IShellFolder::EnumObjects` 探一项——这个命名空间确实
能枚举出东西，但解析名是 `::{26EE0668-…}\0\::{7B81BE6A-…}` 这种复合形式，
**我们自己的 `EnumerateFolder` 解析不了它**，真进去就只有空列表，看起来就是"打不开"。

修法：`EnumObjects` 探到有项之后，再用 `EnumerateFolder(path)` 试一次，
**我们自己的枚举器能列出东西才算容器**。这样"判成容器"和"进去有内容"永远一致。
实测：存储空间、Windows Defender 防火墙、恢复、疑难解答、文件历史记录、电源选项、
字体、Internet 选项双击都能打开各自的面板（日志统一是「按 PIDL 打开成功」）。

## 坑 34：虚拟列表换视图以后必须重建条目数并立即重画

现象：从右键「查看」切到大图标/小图标/列表，画面不变，得把鼠标划过去才一行一行变。

原因：owner-data 列表切换 `LVS_TYPEMASK` 之后，控件内部还留着按旧视图算好的项位置，
只 `InvalidateRect` 的话它按旧位置重画，视觉上就是"没反应"。

修法（`FileListView::SetViewMode` 末尾）：
1. `ListView_SetItemCount` 重报一次条目数，逼它丢掉布局缓存；
2. `RedrawWindow(RDW_INVALIDATE | RDW_ERASE | RDW_FRAME | RDW_ALLCHILDREN | RDW_UPDATENOW)`
   整窗立即重画。
实测：菜单一发下去（鼠标完全不动）画面立刻变成新视图。
### 坑 35：自动化"逐项双击"不能靠跨进程读列表坐标，也不能靠窗口差集判断结果

想批量验证"每一项双击能不能打开"，遇到的三个问题：

1. `LVM_GETITEMRECT`(0x100E) / `LVM_GETITEMPOSITION`(0x1010) 从外部进程发过去，
   owner-data 列表一律返回失败或空 —— 跨进程 SendMessage 传结构体指针不是所有 LVM
   消息都会被封送，拿不到项矩形。
2. 靠"双击前后枚举窗口、看新增了哪些窗口"判断是否打开：不可靠。
   系统面板（设置、设备管理器…）会复用同一个窗口，差集为空；
   而我们关闭窗口是异步的，下一项开始时旧窗口还没关完，差集里出现的是上一次的窗口 → 全错位。
3. 靠截图目测每一行的 y：行距只有 22~25 像素，看缩略图必然偏一两行。
   实测行距 22（不是 25），第一行选中条在 y 73~95。

可用做法（已验证）：
- 坐标用键盘校准：列表单击取得焦点 → `Home` 选中第 0 项 → 截图后扫描某一列像素，
  找"选中行"的蓝色条（B>240、R 150~250、G>200），得到行的上下边界；
  再按 `↓` 一次重新扫描，两条的差值就是行距。本次测得首行 73~95、行距 22。
- 判定结果改为"让程序自己说"：在双击分支里打 `双击：[项目名] 解析名` 日志，
  后面紧跟 `导航到 / 按 PIDL 打开成功 / 打开失败`，按日志归集，100% 准。
- 鼠标停在列表上会产生"悬停高亮"（第二条蓝条），扫描前要把鼠标移到列表外。

### 坑 36：容器判定会抖动 —— 同一个 applet 两次分别走"进目录"和"PIDL 打开"

「程序和功能」「设备和打印机」这类项，`ShellItemIsContainer` 用
`EnumerateFolder` 探一次的方式判定，两次测试分别得到"有内容 → 当容器进去"和
"没内容 → 按 PIDL 打开"，同一个项行为不一样。

目前影响不大：两条路都能出内容（进目录能看到 33/22 项列表，PIDL 打开能弹面板），
用户不会看到"空列表"。但如果以后要做到和系统完全一致（双击直接弹面板），
需要把这类"控制面板二级项"固定成"不导航、一律 PIDL 打开"，
并用一张白名单区分真容器（如「Windows 工具」）。
### 坑 37：表头（列宽）通知不是列表发给你的，是 SysHeader32 发的

拖动"修改日期 / 类型 / 大小"这三列的边界，想法是记一下新宽度存进配置。
一开始在 `WM_NOTIFY` 里只认 `m_fileListView.Handle()`，结果拖完松手什么也没记上。

原因：`HDN_BEGINTRACK` / `HDN_ENDTRACK` 这些通知的 `hdr.hwndFrom` 是**列头控件**
（类名 `SysHeader32`，`ListView_GetHeader` 拿到的那个句柄），不是列表控件自己。
列表只是把列头挂在自己里面，通知的发件人还是列头。

改法：`FileListView` 增加 `HeaderHandle()`（就是 `ListView_GetHeader`），
`MainWnd` 的 `WM_NOTIFY` 转发条件放宽成
`hwndFrom == m_fileListView.Handle() || hwndFrom == m_fileListView.HeaderHandle()`。

判断"哪一列被拖了"用 `HDN_ENDTRACK` 的 `iItem`：0 是文件名列（自适应，不记），
1/2/3 分别是 修改日期/类型/大小，只处理 `iItem >= 1`。

### 坑 38：窗口最大化时 GetWindowRect 记的是"铺满屏幕"的矩形

要记"关窗口时的位置和大小"，第一反应是 `GetWindowRect`。
但窗口最大化时它返回的是整块屏幕（比如 0,0 1920x1080），存下来下次先还原，
用户会看到一个占满屏幕的怪尺寸窗口，再点最大化又变回正常 —— 很别扭。

改法：用 `GetWindowPlacement`，取 `rcNormalPosition`（"还原之后"的矩形），
`showCmd == SW_SHOWMAXIMIZED` 就记 `maximized=true`，启动时 `Show()` 里用 `SW_SHOWMAXIMIZED`。

另：记下来的矩形要检查还在不在显示器上（`MonitorFromRect(..., MONITOR_DEFAULTTONULL)`），
不在就回居中开窗，否则会开出"看不见的窗口"（用户以为程序没启动）。

### 坑 39：控制面板项"是不是容器"不能靠枚举探测，要按路径钉死

`ShellItemIsContainer` 原来的思路：枚举一次，有子项就当容器。
控制面板二级项（applet）在这个探测上不稳定 —— 冷/热 COM 状态下
`EnumerateFolder` 对同一个复合解析名的结果会不一样，
表现是同一个「程序和功能」两次分别"进目录"和"弹面板"。

结论：控制面板里的 applet 系统行为就是**弹面板**，不需要探测。
改成 `IsControlPanelAppletPath()`：解析名前缀是
`::{26EE0668-A00A-44D7-9371-BEB064C98683}\0\` 就当 applet（一律不导航），
白名单放行「Windows 工具」（`::{D20EA4E1-…}`，它真的是容器）。

写代码要注意：源码里字符串必须写成 `\\0\\`，写成 `\0` 会被编译器当成字符串结束符。

## 打开方式（阶段 12）踩到的几条

### 1. 商店应用用 `IApplicationActivationManager::ActivateForFile` 打不开（0x80270254）

本机 Win11 实测：对商店版记事本、照片这类**打包桌面应用**，`ActivateForFile`
一律返回 `0x80270254`，文件根本打不开。一开始怀疑是公寓（主线程是 STA），
改到临时线程 `CoInitializeEx(COINIT_MULTITHREADED)` 里调用，**结果一模一样**；
而同一个线程里 `ActivateApplication`（不带文件）却能成功启动应用 —— 说明
AUMID 是好的，是这个方法对这类应用无效。

正路：`ShellExecuteExW` + `fMask = SEE_MASK_CLASSNAME` + `lpClass = ProgID`。
系统会去读 `HKCR\<ProgID>\shell\open\command` 里登记的
`DelegateExecute = {BFEC0C93-0B7D-4F2C-B09C-AFFFC4BDAE78}`，再按该 ProgID 自带的
`AppUserModelID` 把文件交给应用。实测记事本、照片都能真的打开文件。

所以账本里**必须同时存 ProgID 和 AUMID**：AUMID 用于"程序还在不在"和取图标，
ProgID 用于真正打开。

### 2. `CLSID_EnumerableObjectCollection` 的集合 QI 成 `IShellItemArray` 会失败

自己拼 `IObjectCollection::AddObject` 再 `QueryInterface(IID_IShellItemArray)`，
在 Win11 上直接失败（表现是双击文件报"文件列表准备失败"）。
EnumerableObjectCollection 并不保证对外暴露 `IShellItemArray`。
换 `SHCreateShellItemArrayFromShellItem(item, IID_IShellItemArray, …)` 一次成功。

（这条现在只作为记录：商店应用已经改成 ShellExecuteEx，不再需要文件数组。）

### 3. 启动失败不要记成"程序被卸载了"

`alive = 0` 只由 `IsAvailable`（`SHCreateItemFromParsingName` 解析 exe / `shell:AppsFolder\<AUMID>`）判定后写入。
`Launch` 失败（文件被占用、参数不对、激活失败）只弹提示，**不动 alive**——
否则一次偶发失败会让菜单项凭空消失。

### 4. 窗口"可见但看不见"：`ShowWindow(SW_SHOW)` 会被忽略一次

调试时发现 `IsWindowVisible` 返回 false，`ShowWindow(h, SW_SHOW)` 也不管用；
改成 `SetWindowPos(h, …, SWP_SHOWWINDOW=0x0040)` 才真正显示出来。
（Windows 对进程里第一次 ShowWindow 会用 STARTUPINFO 的 wShowWindow，会被"吃掉"。）

### 5. 锁屏 / 无前台窗口时，所有模拟输入都失效 —— 改用消息驱动

现象：`GetForegroundWindow()` 返回 0、鼠标坐标停在 (0,0)、`SetCursorPos` 和
`keybd_event` 全部失败（`mouse_event` 则静默无效）。这不是权限问题，是输入桌面不可达。
而 `vw_findwindow/getwindowrect/PrintWindow` 仍然正常。

可用的测试手法（全程不需要鼠标）：
- 选中文件列表第 N 项：`SendMessage(listView, WM_SETFOCUS)` 然后
  `SendMessage(listView, WM_KEYDOWN, VK_HOME / VK_DOWN)`（ListView 会乖乖更新选中）；
- 触发"打开"：`PostMessage(mainWnd, WM_COMMAND, 3201)`；
- 关掉模态的设置窗口：`PostMessage(dialog, WM_CLOSE)`（等价于点"关闭"，会保存配置）；
- 截图：`PrintWindow(hwnd, hdc, PW_RENDERFULLCONTENT=2)`，被别的窗口遮挡也能画出来。

### 6. 系统复选框 + `NM_CUSTOMDRAW` 改不掉「选中行」的蓝底白字

设置窗口要照参考窗口做成浅蓝底深色字的选中行，先试了 `LVS_EX_CHECKBOXES` +
`NM_CUSTOMDRAW`：`CDDS_ITEMPREPAINT` 里设 `clrTextBk = RGB(232,240,254)`、返回
`CDRF_NEWFONT`，普通行能改，**选中行永远是系统高亮色**（`clrTextBk` 对选中项不生效；
返回 `CDRF_SKIPDEFAULT` 又得自己把每一列连同文字全画一遍）。
最终把列表改成 `LVS_OWNERDRAWFIXED` 整行自绘（`WM_MEASUREITEM` 给行高、
`WM_DRAWITEM` 自己画复选框/图标/文字/圆点），才彻底可控。
注意：去掉 `LVS_EX_CHECKBOXES` 后，`ListView_Get/SetCheckState` 全部失效，
勾选状态必须自己存在数据里（这里是 `m_entry.items[i].enabled`）。

### 7. 拿空 DC 量文字宽度会得到 0

`DrawTextW(nullptr, text, -1, &rect, DT_CALCRECT)` 量出来的宽高是 0，
「默认程序」四个字于是只画出一个竖条。必须先选真实字体、用真实 DC：
`GetDC(hwnd)` → `SelectObject(dc, m_font)` → `GetTextExtentPoint32W(...)`。

### 8. `NM_CLICK` 里不能用 `GetMessagePos()` 判断点在哪

`NM_CLICK` 是 `WM_NOTIFY` 带来的，处理它的时候全局鼠标位置可能已经变了
（自动化 PostMessage 场景下更是恒为 (0,0)）。应当直接读通知结构：
`NMITEMACTIVATE::iItem` 和 `NMITEMACTIVATE::ptAction`（客户区坐标）。

### 9. 列表的白底会盖掉外框的圆角

外框用 `RoundRect` / GDI+ `GraphicsPath` 画圆角本来是对的，但框里塞的是 ListView，
它是个直角矩形、白底/选中底色直接把四个角盖住 —— 看起来"根本没有圆角"。
给列表 `SetWindowRgn(CreateRoundRectRgn(...))` 裁了同样的圆角，接缝仍然生硬；
用户最终拍板**改直角**（1px 矩形线，颜色 `RGB(232,235,239)`），彻底绕开这个问题。
结论：在 Win32 里给"矩形子控件"套圆角容器，成本远大于收益。

### 10. `SM_CXVSCROLL` 无脑预留会在右侧留一条空白

列宽算成 `客户宽 - 状态列 - 默认列 - SM_CXVSCROLL - 4`，不管当前有没有滚动条，
右边永远空出 21px。改成"行数 × 行高 > 可视高度"时才扣滚动条宽度。
另外行分隔线不该按列宽总和画（会更短），要按列表**客户区**宽度画，
并两端各缩进 3px（`kRowLineInset`），这样线两端离表格边框一致。

## 设置按钮与右键「新建」菜单（2026-11-15）

### 11. 系统的「新建」菜单不是直接扫 HKCR，先读它自己那份清单

资源管理器的「新建」列表来自
`HKCU\Software\Microsoft\Windows\CurrentVersion\Explorer\Discardable\PostSetup\ShellNew`
的 `Classes` 值（REG_MULTI_SZ）——本机 14 行。只扫 `HKCR\.ext\ShellNew` 会漏掉
`Folder` 这种 ProgID 行，菜单项就会比系统少一大截。

另外模板要查**三个视图**：`HKCR\<行>\ShellNew`（64 位）、
`HKCU\Software\Classes\<行>\ShellNew`、`HKCR\Wow6432Node\<行>\ShellNew`（32 位）。
WinRAR、WPS 都是 32 位程序，模板登记在最后那个位置。

### 12. 清单里的项不代表注册表里有模板

本机 `Classes` 里有 `.doc .docx .ppt .pptx .xls .xlsx .rtf`，但它们**三个视图都没有
ShellNew**（软件卸载残留）。系统菜单照样显示这些项，所以要按"建空文件"兜底，
否则菜单看起来就是"少很多"。

反过来的情况也存在：`.bmp` 和 `.txt` 注册表里没有 ShellNew，
但系统菜单一直有「BMP 图像」「文本文档」——这是 Windows 内置项，要自己补。

### 13. 系统菜单会隐藏"点了也没用"的项

- `.library-ms`（库）：ShellNew 里有 `Handler`（一个 COM 处理器），处理器不可用时
  系统不显示这一项。
- `.contact`（联系人）：ShellNew 里 `Command` 指向 `C:\Program Files\Windows Mail\Wab.exe`，
  Windows Mail 卸载后程序不在，系统也不显示。

所以枚举完要过滤：非 `.lnk` 的 Handler 项跳过；Command 项检查命令里的第一个程序
是否还存在（`GetFileAttributes`），不存在就跳过。

### 14. `.lnk` 的 ShellNew 是 Handler + NullFile，不能直接建空文件

直接 `CreateFile` 建出来的 `.lnk` 是坏文件（双击报错）。资源管理器实际是弹
「创建快捷方式」向导：`rundll32.exe appwiz.cpl,NewLinkHere "<目录>"`。

### 15. `Command` 类型的 ShellNew 要真的执行，`%1` 换成目标目录

WPS 的「新建 PDF 文档 / WPS AI 生成 PPT」就是这样注册的，命令本身不含 `%1`。
之前只弹"需要外部程序支持"，改成 `CreateProcessW` 执行，工作目录设为当前文件夹。

### 16. `RegQueryValueEx(hKey, nullptr, …)` 读默认值在本机读不出来

想拿 `HKCR\.zip` 的默认值（ProgID `WinRAR.ZIP`）来判断类型名，
`RegOpenKeyExW(HKEY_CLASSES_ROOT, ".zip", …, KEY_READ | KEY_WOW64_64KEY)`
再 `RegQueryValueExW(key, nullptr, …)` 一直返回空（同一个键用 PowerShell 能读到）。
换成一次到位的 `RegGetValueW(HKEY_CLASSES_ROOT, ".zip", nullptr, RRF_RT_REG_SZ, …)`
立刻正常。

### 17. 菜单文字要按 ProgID 求，不能按扩展名求

`AssocQueryString(ASSOCSTR_FRIENDLYDOCNAME, ".zip")` 得到的是系统内置的
「压缩(zipped)文件夹」；按 ProgID `WinRAR.ZIP` 求才是
「WinRAR ZIP 压缩文件」——后者才是资源管理器菜单显示的写法。
所以顺序是：`MenuText` → ShellNew 默认值 → 扩展名默认值（ProgID）→ 按 ProgID 求名
→ 按扩展名求名 → `SHGetFileInfo` 的 `szTypeName`。

（`ASSOCSTR_FRIENDLYDOCNAME` 的枚举值是 3，`ASSOCSTR_FRIENDLYAPPNAME` 才是 4；
传 4 会拿到「记事本」这种程序名。）

### 18. 菜单图标优先读 ShellNew 的 `IconPath`

`IconPath` 形如 `C:\WINDOWS\system32\shell32.dll,-16769` 或 `C:\…\wab.exe,1`：
去掉前导 `@` 和引号，按最后一个逗号拆成"文件 + 索引"，
再用 `SHDefExtractIconW(file, index, 0, nullptr, &small, 16)` 取 16px。
负数索引表示资源 ID，要原样传下去。

### 19. 自绘菜单项的两个小坑

- `WM_MEASUREITEM` 里量的宽度要按 `MF_OWNERDRAW` 的项单独算（图标位 + 文字宽 + 留白），
  高度取 `SM_CYMENU`，否则菜单行会挤扁。
- `DrawTextW` 默认会处理 `&` 快捷键标记，正好和系统菜单一致（MenuText 里的
  「文件夹(&F)」显示成「文件夹(F)」+ 下划线），不需要自己去掉 `&`。
### 20. 右键菜单的分组不能照 IShellFolder 的背景菜单抄

用 COM 把目录的背景菜单（`IShellFolder::CreateViewObject(IID_IContextMenu)`）dump 出来，
里面只有第三方扩展和「新建」「属性」：

    使用 Visual Studio 打开 / Open Git GUI here / Open Git Bash here / 授予访问权限 /
    SVN 检出 / 新建 / 属性

「查看」「排序方式」「粘贴」「刷新」这些**是资源管理器的视图（ShellView）自己注入的**，
不在 IShellFolder 的背景菜单里。所以自研的「查看」「粘贴」「刷新」只能按资源管理器
实际显示的顺序自己排，不能指望从 shell 接口里 dump 出来。

另外：文件 / 文件夹 / 多选的菜单要 `IShellFolder::GetUIObjectOf(IID_IContextMenu)`，
在 .NET 侧用 COM 互操作调这个函数很容易崩（`apidl` 要按 `IntPtr` + `Marshal.AllocCoTaskMem`
组数组传，接口声明少一个方法就会错位），实测直接 0xC0000005。这条路不值得再试。

### 21. 「在新窗口中打开」靠命令行参数，不需要额外的窗口管理

`wWinMain` 原来不解析 `lpCmdLine`。`ShellExecuteW(自身exe, "\"目录\"")` 启动自己，
再在 `wWinMain` 里把 `lpCmdLine` 去掉首尾空白与成对引号当启动目录就够用。
注意 `MainWindow::Create` 要多一个初始目录参数，且 WM_CREATE 里要
"参数可用就用参数，否则回上次停的目录"，否则第二个窗口会跟着配置跑到别的地方。

### 22. 多选属性要自己组 IDataObject

系统的「多个项目属性」窗口入口是 `SHMultiFileProperties(IDataObject*, 0)`。
IDataObject 用 `SHCreateDataObject(目录PIDL, 个数, 子项PIDL数组, nullptr, IID_IDataObject, &p)` 造：

- 目录 PIDL：`SHParseDisplayName(父目录路径)`；
- 子项 PIDL：每个文件 `SHParseDisplayName` 后取 `ILFindLastID()`（只要最后一段）；
- 拿到的 PIDL 都是 `CoTaskMemAlloc` 出来的，用完要 `CoTaskMemFree`。

组不起来（比如选中项里有 `::` 虚拟项）就退回"只显示第一个"的单对象属性。
### 23. 回收站的"原来在哪个目录"属性要运行时取键

回收站项的 `System.Recycle.DeletedFrom`（原目录）在 SDK 的 `propkey.h` 里**没有**
`PKEY_DeletedFrom` 这种现成常量（整个 SDK 头文件都搜不到），直接写 `PKEY_DeletedFrom`
编译不过。正确做法是运行时按属性名取键：

    PROPERTYKEY key;
    PSGetPropertyKeyFromName(L"System.Recycle.DeletedFrom", &key);   // 需要 propsys.lib

拿到 key 再走 `IShellItem2::GetString(key, &text)`。取不到键时 `GetString` 会失败，
当成"不支持还原"处理即可，别硬往下走。

### 24. IFileOperation::MoveItem 的目标是 IShellItem，不是路径字符串

`IFileOperation::MoveItem(psiItem, psiDestinationFolder, pszNewName, pfops)`：
第二个参数是 `IShellItem*`（目标文件夹），不是 `LPCWSTR`。传字符串会直接编译报错。
目标文件夹要先用 `SHCreateItemFromParsingName(目录, nullptr, IID_IShellItem, …)` 包一下，
用完 Release。`pszNewName` 传 `nullptr` 表示"名字不变"。

### 25. 撤销记录只能在操作成功后写

复制 / 移动 / 删除都走后台线程（`RunFileOperationAsync`），用户在系统进度框里
点了取消、或者中途失败时，`WM_APP_OPERATION_DONE` 带回的是失败码。
撤销记录必须写在 `SUCCEEDED` 分支里，否则菜单上会出现一个"撤销 删除"但按下去
什么都没发生——比没有这一项更糟。

另外粘贴时如果目标目录已有同名文件，系统会自动改名成「xxx (2).txt」，
我们按"目标目录 + 源文件名"算出来的 afterPaths 就对不上。这种项撤销时静默跳过，
不影响同一批里的其它项。
