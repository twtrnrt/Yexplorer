# 同步状态图标覆盖层（Overlay 角标）设计评估

> 状态：**方案已拍板，业务代码尚未动手**。本文记录可行性、方案、设置交互、工作量、
> 资源占用与风险，按分期落地。最后更新：2026-11-22。
>
> 已拍板：主界面为总开关复选框「显示同步状态」+ 配置按钮；各套的「路径范围 + 优先级」
> 收进独立配置窗口（路径复选框 + 路径白名单 + 序号/↑↓，不做拖拽）；总开关关闭时
> 懒加载、行为等价现状。详见 4.4。

## 1. 背景与目标

有些软件会给文件/文件夹加同步/版本状态角标：Git、SVN（TortoiseGit / TortoiseSVN）、
百度网盘、OneDrive 等。原生资源管理器在主图标左下角叠一个小图标表示状态。

目标：本文件管理器同样显示这些系统注册的角标，**体验与原生一致**——不自己判断
"改没改、同步没同步"，只把系统已有处理器的结果取出来叠上去。

本机实测注册的处理器（`HKLM/HKCU\...\Explorer\ShellIconOverlayIdentifiers`）共 20 来个：

- OneDrive1~7：7 个同步状态；
- Tortoise1~9：9 个版本状态（Normal / Modified / Conflict / Locked / ReadOnly /
  Deleted / Added / Ignored / Unversioned），共用 `TortoiseOverlays.dll` 共享桥接，
  真正状态由安装的 Git/SVN 客户端提供；
- aPipIconOverlay、EnhancedStorageShell、Offline Files 等。

## 2. Windows Overlay 机制（原理）

1. 软件安装后把一个 COM 处理器登记到注册表
   `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Explorer\ShellIconOverlayIdentifiers\<名字>`
   （`HKCU` 同样位置也可），默认值是处理器 CLSID。
2. 资源管理器画完主图标后，按优先级逐个问处理器
   `IShellIconOverlayIdentifier::IsMemberOf(pszPath, dwAttrib)`（第二参是
   DWORD 文件属性，不是 PIDL）；命中就用处理器
   `GetOverlayInfo` 提供的小图标叠在主图标左下角。
3. 公开接口：`IShellIconOverlayIdentifier`，自研程序可直接调用。

### 命中与优先级规则（必须与原生一致）

- **每个图标最多叠一个角标**：按优先级依次问，第一个命中的就用，后面不再问；
  不会把多个角标都画上。
- **优先级 = 注册表名称排序**：名字前导空格越多越靠前（原生调顺序的惯例）。
- **系统只取前 15 个**处理器，排在 15 名之后的原生就不生效，程序照搬同样截断。
- 同一家内部的多个状态处理器互斥，只命中当前状态那一个。

### Git + SVN 同目录的行为

目录里同时有 `.git` 和 `.svn` 时，两套处理器的 `IsMemberOf` 都会判定命中自己，
但界面只显示**排序靠前那一套**；显示 Git 还是 SVN 取决于注册表顺序（安装先后、
空格前缀）。这是原生本身的行为，原生资源管理器里同样只出一套角标。程序不自己挑，
照搬优先级即可。技术上可以改成叠两套，但会与原生不一致，不做。

## 3. 现有基础（已核实，可复用）

- 图标架构：主图标直接引用系统图像列表（`SHGetImageList`），按扩展名 / 路径 / PIDL
  取索引；图标缓存在 `src/shell/ShellIcon.{h,cpp}` 的 `IconCache`。
- **已有图标合成先例**：`IconCache::CreateDimmedIcon` / `GetDimmedIconIndex`
  （剪切/隐藏项半透明）。套路是：原图标画进 32 位带 alpha 的 DIB → 处理 →
  `CreateIconIndirect` 转回 HICON → `ImageList_ReplaceIcon` 追加进同一图像列表 →
  按原索引缓存新索引。Overlay 合成复用这套。
- **主列表唯一图标出口**：`FileListView::IconIndexForEntry`（`src/ui/FileListView.cpp`），
  三处消费：自绘小图标、平铺格子、`LVN_GETDISPINFO`。
- `IsMemberOf` 需要完整路径 + 文件属性（`GetFileAttributesW` 取得）；`ShellEntry::pidl` 不传给该接口。
- 枚举在后台线程（已 `CoInitializeEx`）；图标索引在 UI 线程取。
- 导航栏 `NavigationPane` 单独调 `IconCache`，不走 `IconIndexForEntry`，是第二接入点。

## 4. 方案设计

### 4.1 新增 overlay 管理模块（建议 `src/shell/ShellOverlay.{h,cpp}`）

**A. 处理器注册表（懒加载，按套归并）**

- **懒加载**：不在启动时无条件实例化。总开关勾上时才去读注册表、实例化处理器；
  总开关关闭时整套不初始化，不读注册表、不加载图标，
  行为与未做本功能前完全一致。
- 读 HKLM / HKCU 两处 `ShellIconOverlayIdentifiers`，按名称排序得到默认优先级；
- 同族处理器归并成**一套**：依据 `InprocServer32` 的 DLL 路径相同 / CLSID 号段相近。
  注意 TortoiseGit 与 TortoiseSVN 共用 `TortoiseOverlays.dll` 桥接，分不到两家，
  合并为一个「Tortoise」项。
- 每个 CLSID `CoCreateInstance` 出 `IShellIconOverlayIdentifier`；
- 调 `GetOverlayInfo` 取 overlay 小图标（HICON 或资源路径），按尺寸缓存；
- 不实现接口、实例化失败的跳过；遵循前 15 个上限；后装的新套默认排末尾。

**B. 条目判定（先本地范围过滤，再按顺序询问，按路径缓存）**

- 判定前先按配置确定**启用集合**和**询问顺序**（见 4.4）；
- **先做本地路径范围过滤**：某套为白名单模式时，条目路径不在其 `paths` 前缀
  （含子目录）内，直接跳过这套，**不调用处理器**；范围外条目无处理器询问开销；
- 在后台枚举线程对通过范围过滤的项，按顺序依次问 `IsMemberOf(路径, 文件属性)`；
- 第一个命中即记录该套 / 状态标识，存入 `ShellEntry` 新字段 `overlayId`；
- 命中 / 未命中都按路径缓存，避免重复问处理器。

**C. 图标合成**

- 复用 DIB 套路：主图标画满幅，overlay 小图标贴左下角（原生约占主图标 1/4）；
- 合成新 HICON 追加进图像列表；
- 缓存键 = 主图标索引 + `overlayId`，与现有半透明缓存同理。

### 4.2 接入点

- **主列表（第一期 MVP）**：`IconIndexForEntry` 末尾，主索引确定后查 `overlayId`，
  有则合成。
- **导航栏（已决定不做）**：曾实现过一版（后台判定节点路径后换 ImageList 索引），
  实机后用户判断价值有限、还要多养一条判定链路，整段 revert 掉了。导航栏不再显示角标。

### 4.3 线程模型（关键风险点）

- 处理器多为 STA。判定重活放后台枚举线程（已初始化 COM），结果存进 `ShellEntry`；
  UI 线程只按 `overlayId` 合成图标，不碰 COM。
- 不在 UI 线程按需实例化处理器，避免 apartment 问题和卡顿。

**一期现状与风险（2026-11-22 复核，二期待加固）**

- 一期实现是「第一次枚举时在那根后台线程里 `CoCreateInstance` 实例化，对象存进单例
  `OverlayManager::m_handlers`，之后每次切目录新起一根 STA 枚举线程跨线程复用旧对象」。
  STA 对象的线程亲和性要求只在创建它的线程上调用，跨线程可能返回
  `RPC_E_WRONG_THREAD (0x8001010A)` / `RPC_E_SERVER_DIED (0x8001010D)`；一期
  `ResolveEntry` 对非 `S_OK` 一律按未命中兜底，症状是「角标偶尔不显示」，不会崩。
- 枚举线程本身是**串行**的：起新线程前先 `join` 旧线程并 `m_enumToken.Cancel()`，
  `m_handlers` 不存在并发竞争，问题只在「对象跨线程」这一点上。
- 实测日志暂未出现 `RPC_E_WRONG_THREAD`；豆包那套报的是 `0x8007045A`
  （DLL 初始化例程失败），在实例化阶段即被跳过，与线程模型无关。
- **已落地（2026-11-23）：方案 2A「常驻专用 STA 线程」** —— 管理器内部起一根不随枚举
  结束而退出的 STA 工作线程（带消息泵，`MsgWaitForMultipleObjectsEx` + `PeekMessage`），
  处理器的创建 / `GetOverlayInfo` / `IsMemberOf` / 释放全部固定在这根线程；枚举线程与
  UI 线程通过「投递任务 + 等完成事件」拿结果。运行时多一根常驻线程（虚拟栈 1MB 保留、
  实际提交约 8~32KB，空闲时阻塞等事件、CPU 占用 0），内存增量可忽略。
- **不采用 2B「每线程重建对象」**：每次切目录重新 `CoCreateInstance` 全部处理器有启动
  开销，且若最终演进到 2A，这部分改动会被覆盖，属于可跳过的中间态。

### 4.4 设置交互（已拍板）

**主设置界面（保持现有固定布局，不做内嵌动态列表）**

- 一个**总开关复选框**「显示同步状态」：
  - 勾上：开启角标功能，按配置窗口里的规则询问处理器；
  - 不勾：不初始化处理器、不询问、不合成，图标走原有流程，等价现状；
- 总开关**右侧**放一个「配置…」按钮；总开关不勾时该按钮**置灰不可点**；
- 不再提供"固定某一套"模式：所有启用的套都按优先级顺序参与，第一个命中的显示。

**配置窗口（点「配置…」按钮打开）**

- 列表每项一行，分三列：**优先级 / 应用名 / 显示范围**；
- **优先级列**：序号（1、2、3…）+ ↑ / ↓ 按钮，序号与箭头合起来统称「优先级」；
  序号表示当前先后顺序，上下移动即调整顺序（做法 B，不做鼠标拖拽）；
- **应用名列**：即原来的套名；同族的多个状态处理器并成一项，不暴露
  `OneDrive1`、`Tortoise2Modified` 这种槽位名；取不到可读产品名时退回注册名；
- **显示范围列**：包含复选框 + 路径区；没有独立的"启用整套"复选框，整套是否
  参与由路径配置推导（见下）：
  - **复选框勾上**：路径区显示「处理全部路径」，隐藏路径按钮和添加入口，
    这套对所有路径生效；
  - **复选框不勾**：白名单模式，依次排已选路径，路径区**末尾**是一个「+」按钮用于
    添加路径；这套**只处理列出的路径及其子目录**（白名单递归到子目录）；
  - 已添加的每个路径显示为一个**小按钮（chip）**：正常宽度下按钮上显示文件夹名，
    鼠标悬停 tooltip 显示完整路径，按钮上带「×」可删除；多个路径一行放不下、chip
    被挤得过窄时，chip 上省略文件名、只保留「×」删除按钮，但悬停仍要能显示完整路径；
- **整套禁用的判定**：复选框不勾、且路径列表为空 → 这套一条路径都不处理，等于禁用；
- 弹窗「确定 / 取消」：确定才落配置，取消丢弃本次改动。

**配置字段（`settings.json`）**

- `overlayEnabled`：总开关，布尔值；
- `overlaySets`：各套配置数组，每项 `{ id, scope: "all" | "list", paths: [] }`；
  `scope=all` 处理全部路径；`scope=list` 只处理 `paths` 及其子目录；
  `scope=list` 且 `paths` 为空即禁用该套；
- `overlayOrder`：各套标识的优先级顺序数组（序号即此数组下标）；
- 未记录过的新处理器默认 `scope=all`、追加到末尾，保证装新软件后角标正常出现。

**说明**

- 配置只管「哪一套、在哪些路径下参与」；具体显示对号还是感叹号，由该套按当前目录状态判定。
- 路径白名单按目录前缀匹配，命中目录及其所有子目录。
- 改完设置重新枚举当前目录、重画即生效；不做主动监听刷新（见 7.5）。

### 4.5 内置 Git 状态判定（方案 B：调 `git.exe`，2026-11-23 定案）

**背景**：Git for Windows 本体（`git.exe`、Git Bash、git-gui）**不注册任何覆盖图标处理器**——
角标是 Windows Shell 扩展，Git 上游只做命令行。所以只装了 Git、没装 TortoiseGit 的机器，
Git 仓库在原生资源管理器和本程序里**都完全没有角标**（本机实测：17 个注册项里 Tortoise1~9
全指向 `TortoiseOverlays.dll`，只挂了 SVN，没有任何 Git 项）。内置这一路的唯一目的就是补这个空白。

#### 4.5.1 方案选型

| 方案 | 代码量 | 准确度 | 依赖 | 结论 |
|---|---|---|---|---|
| **B. 调 `git.exe`（已选）** | 300~500 行 | 最高（就是 Git 本尊） | 用户需装 Git | **采用** |
| C. 引入 libgit2 静态库 | 700~900 行 | 高（99%） | 无外部依赖，但 exe +1~2MB、GPLv2 链接例外许可 | 备选，B 不满足时再换 |
| A. 自研解析 `.git/index` + stat | 1500~2000 行 | 约 90%（边角会错） | 无 | **不采用** |

- 选 B 的理由：代码量只有 C 的三分之一、准确度最高、当天可出可用版；判定的"数据层"与 C 完全同构
  （都是一张「路径 → 状态」表给管线查），以后若改用 libgit2，上层接线可原样复用。
- 不选 A 的理由：要做到和 Git 一样准，必须读 zlib 压缩的对象算 SHA-1，还要实现完整 `.gitignore`
  语义（嵌套、否定、目录规则、全局 excludesfile），工作量比 C 还大、准确度反而最低；只做 stat 比对
  会持续误报（内容没变但 mtime 变了也一直显示"修改"）。
- libgit2 的成本已评估过，结论留档：许可证为 **GPLv2 + 链接例外**（允许静态链入任何程序，不传染；
  仅修改 libgit2 本身才需开源）；CMake 构建用 `BUILD_SHARED_LIBS=OFF` + `STATIC_CRT=ON`（MSVC 静态
  CRT，正好匹配本项目 `/MT`）+ `USE_BUNDLED_ZLIB=ON`（零外部依赖）+ 关掉 SSH/HTTPS/测试/CLI；
  版本选 1.9.x 稳定版（main 上 2.0 尚在开发）。

#### 4.5.2 探测 `git.exe`

按顺序找，命中即用，结果进程内缓存一次：

1. `%ProgramFiles%\Git\cmd\git.exe`、`%ProgramFiles%\Git\bin\git.exe`
2. `PATH` 里的 `git.exe`
3. 注册表里 TortoiseGit 记录的 Git 路径（装了 TortoiseGit 必然装了 Git for Windows——它底层就靠 `git.exe`）
4. Git for Windows 的非默认安装位置（按卸载信息里的 InstallLocation 找）

**找不到就整套不启用**：内置这套不出现在配置窗口列表里，行为退回现状（只有 COM 处理器）。
这不是错误状态，不写 error 日志，只写一条 info 说明未检测到。

#### 4.5.3 数据流与线程（关键，避免踩 2A 的坑）

```
枚举线程（StartEnumeration 的后台线程）
   ├─ 枚举目录条目 → entries
   ├─ GitStatus::BeginDirectory(当前目录)   ← 起 git.exe、解析出状态表（本线程内完成）
   ├─ OverlayManager::Annotate(entries)     ← 投递到常驻 STA 线程，同步等结果
   │     └─ ResolveEntry 遇到内置 Git 那一路时，查 GitStatus 的表（只读）
   └─ GitStatus::EndDirectory()             ← 清表
```

- **`git.exe` 的调用放在枚举线程，不进常驻 STA 线程**：常驻线程是给 COM 处理器用的，
  不能被一个外部进程阻塞几十到上百毫秒。
- 表在 `BeginDirectory` 建好之后**只读**；`Annotate` 期间枚举线程正阻塞在 `PostTaskAndWait`
  上，不会并发写，因此不需要给表加锁（这一点在代码注释里要写清楚，避免后人误加）。
- 超时与失败都不抛异常：拿不到表就当"内置 Git 未命中"，其余 COM 处理器照常判定。

#### 4.5.4 调用与解析

- 命令行：`git -c core.quotepath=false -C <当前目录> status --porcelain=v2 -z --untracked-files=normal --ignore-submodules=all`
- `CreateProcessW` 带 `CREATE_NO_WINDOW`（不闪黑框），stdout 重定向，边读边等避免管道写满阻塞；
  总超时 5 秒，超时 `TerminateProcess` 并按无结果处理。
- `-z` 用 NUL 分隔、路径不做引号转义，中文路径和空格不会出问题；行首类型字符：
  `1` 普通变更、`2` 重命名/复制（带原路径）、`u` 未合并、`?` 未跟踪、`!` 忽略。
- 输出按 UTF-8 解析（`git.exe` 在 Windows 上输出 UTF-8）。

#### 4.5.5 状态归并与角标种类

原始状态有二十几种组合（两位：X = index 与 HEAD 的差异、Y = 工作区与 index 的差异），
一个图标只能挂一个角标，按下面的优先级归并：

| 角标 | 优先级 | 对应原始状态 |
|---|---|---|
| 冲突 | 1（最高） | `u` 行（`UU / AA / DD / AU / UA / DU / UD`） |
| 修改 | 2 | `M ` / ` M` / `MM` / `R ` / `T ` |
| 新增 | 3 | `A ` |
| 删除 | 4 | `D ` / ` D` |
| 未跟踪 | 5 | `?` 行 |
| 忽略 | 6（默认不显示） | `!` 行 |
| 干净 | — | 无角标 |

- **不区分"暂存与否"**：`git add` 过的修改仍显示"修改"，`git add` 过的新文件显示"新增"。
  角标表达的是"有没有未提交的变化"，跟 Tortoise 口径一致。
- **不显示**：ahead/behind（与远端比较）、当前分支、stash、子模块内部状态（用
  `--ignore-submodules=all` 明确跳过）。

#### 4.5.6 目录的状态怎么来

Git 不提供"目录状态"，目录角标由**归纳**得出：

- 表里所有以该目录为前缀的路径，取其中**优先级最高**的状态作为该目录的角标。
- 因此"某个子文件夹里有一个冲突文件"，整条父目录链都显示冲突；只有未跟踪文件则显示未跟踪。
- 已删除的文件本身不出现在列表里，但"该目录下有删除"会体现在目录角标上（优先级 4）。

#### 4.5.7 接入点（沿用"虚拟处理器"做法，最小改动）

- `OverlayHandler` 加 `builtinKind`（`None` / `Git`）；内置这一路 `handler` 为空、
  `setId = "builtin:git"`、`displayName = "Git（内置）"`。
- `ResolveEntry()` 遇到内置那一路时改调 `GitStatus::Resolve(path)`，不碰 COM。
- `GetOverlayIcon()` 对内置那一路从我们的资源取角标 HICON（按尺寸缓存）。
- `ListSets()` 把内置这套追加进列表 → **配置窗口、优先级上下调、显示范围、失败熔断全部自动复用**。
- 配置存储沿用 `overlaySets`：`id = "builtin:git"`、`name = "Git（内置）"`、`allPaths` 默认 true。
- **同族互斥**：`ScanRegistry` 结果里若存在 Git 类 COM 处理器（DLL 名含 `tortoisegit` / `tgit`），
  内置这套自动置为不参与判定（避免同一目录两路各出一个角标）。
- 默认优先级排在所有 COM 处理器**之后**（有 TortoiseGit 时让它优先），可在配置窗口里往前调。

#### 4.5.8 性能保护

- 只对**当前目录**跑一次命令，用 `-C <当前目录>` 限制范围，不扫整个仓库。
- 条目数超过阈值（2 万）直接跳过内置判定并写一条 info 日志。
- 输出行数超过阈值（3 万）只保留前若干条并降级（防止未忽略的大目录把解析拖死）。
- 结果表跟着现有"每次枚举清空"的语义走（`RunAnnotateOnWorker` 本来就每次清 `m_resultCache`），
  不常驻、不做 LRU。

#### 4.5.9 已知限制（要写进 README / 帮助）

- 未跟踪目录默认只标目录本身（`-untracked-files=normal`）；进入该目录后会重新算，那时才逐项显示。
- 忽略项默认不显示（配置里留开关的话另说）。
- 与远端是否同步（ahead/behind）不显示，只看本地未提交变化。
- 用户没装 Git for Windows → 整套不启用。

#### 4.5.11 分阶段与验收

- **阶段 1（约 1 天，300~500 行）**：`src/shell/GitStatus.{h,cpp}`——git.exe 探测、进程调用与解析、
  状态表、目录归纳、阈值保护；配单测（构造临时仓库覆盖 修改/新增/删除/未跟踪/冲突/干净）。
- **阶段 2（半天）**：虚拟处理器接入（`builtinKind`、`ResolveEntry` 分支、`GetOverlayIcon`、

- **阶段 3（半天）**：5 类角标的三档尺寸资源（自绘，不复用 Tortoise 的图标文件）+ 收尾。

## 5. 缓存与资源占用

| 项 | 策略 | 占用 |
|---|---|---|
| 处理器对象 + overlay 图标 | 全局一份，总共十几个 | 可忽略 |
| 判定结果 | 按路径缓存，**生命周期跟当前目录，切目录即清空**（不做常驻 LRU） | 取决于条目数，带上限 |
| 合成图标 | 按「主索引 + overlayId」组合缓存，不重复合成 | 组合数有限 |

**主要成本在判定**：Tortoise / 网盘处理器内部要查 `.git`、同步库等状态，逐项问有开销。
必须只对已枚举 / 可见项判定并缓存，不能后台全量遍历。

**白名单模式的范围外开销**：某套配成白名单后，范围外条目在本地做路径前缀匹配即跳过，
不调用处理器，这部分文件夹没有询问开销；只有白名单内（含子目录）的条目才会被问。

**对未同步目录的影响（已评估）**

- 没纳入版本控制 / 同步的目录，也要被各套问一遍才能确认「不归谁管」，这步省不掉；
- 正常处理器对未管理目录快速返回未命中；首次打开有新增询问开销，第二次同目录走
  路径缓存，基本无感；
- 询问放后台线程，不卡界面；处理器出错按未命中兜底；
- 目录级粗判（先扫目录标记再决定是否整目录跳过询问）：**第一期不做**。各家标记位置 /
  名字不同，自己猜容易漏判；先靠后台线程 + 路径缓存，条目多的目录实测慢了第二期再加。
- 实际耗时取决于第三方处理器质量，条目很多的目录或质量一般的客户端，首次加载
  可能能感觉到慢一点，需第一版跑起来实测。

## 7. 风险与难点

1. **COM 线程模型**：判定放后台 STA 线程，UI 线程不碰 COM（见 4.3）。
2. **第三方处理器质量参差**：个别 `IsMemberOf` 可能卡顿甚至崩。**第一期先用 HRESULT
   兜底**：调用失败按未命中跳过这套；不做独立进程隔离。COM 无原生超时，若实机遇到
   卡死的处理器，第二期再加固。**已落地（2026-11-23）：3B「异常拦截」+ 3C「失败熔断」**
   ——3B 在调用外层用结构化异常保护包一层（`__declspec(noinline)` 单独成小函数，绕开
   MSVC「需要对象展开的函数不能用 `__try`」的 C2712 限制；栈溢出继续外抛）挡住访问违例；
   3C 连续 3 次失败/异常即熔断、本次会话不再询问该套（`S_FALSE` 属于正常应答，不清零也
   不累计）；两者运行时开销近零。**3A「独立进程隔离」不做**：约 600~1000 行 + 新增辅助
   进程工程，常驻内存 30~80MB（进程基础开销 + 各第三方 DLL），每次判定跨进程往返比进程内
   慢一个数量级，几百个文件同时判定会明显掉速；现有 5 套处理器均为知名软件，触发概率低，
   等真收到崩溃现场再评估。
3. **与现有半透明的叠加顺序**：剪切 / 隐藏项先淡化主图标；原生 overlay 不随主图标
   淡化，叠在淡化层之上。顺序需对齐。
4. **三档尺寸**：16 / 32 / 48 都要合成。位置 / 比例照原生经验值——贴左下角、边长约
   小图标/列表/详细信息 16px、大图标/平铺 32px；第一版截图跟系统对一眼再微调，不做用户可配置。
5. **状态实时刷新**：网盘「同步中 → 完成」、Git 提交后状态变化，缓存要失效重查；
   MVP 先靠切目录 / 手动刷新重建，不做主动监听。
6. **虚拟项**：控制面板等无路径项，处理器一般不覆盖；传路径空、属性 0 兜底。
7. **内置判定与 COM 处理器并存（二期）**：若二期加内置 Git 判定（见 4.5），同一目录可能被
   内置和 COM 两路都判出状态。靠统一优先级管线 + 同族互斥避免重复叠加；两路结果冲突时
   取优先级靠前的一路。第一期纯复用 COM，不存在此问题。

## 8. 分期建议

- **第一期（MVP）**：主列表视图接入，读系统处理器、左下角叠加、按路径缓存；
  导航栏、实时刷新不做。
- **第二期**（2026-11-23 落地情况）：跨线程加固（方案 2A 常驻专用 STA 线程，见 4.3）、
  异常处理器隔离加固（3B 异常拦截 + 3C 失败熔断，见第 7 节）、处理器用途黑名单过滤已落地；
  **导航栏接入已实现后按用户决定撤回、不再做**；**仍待做：缓存失效刷新、选中 / 淡化叠加细节
  对齐**；内置 Git 判定方案已定为「调 `git.exe`」（见 4.5，备选才是 libgit2）。独立进程隔离（3A）记清单不做，等真收到
  崩溃现场再评估。
