# 同步状态图标覆盖层（Overlay 角标）设计评估

> 状态：**方案已拍板，业务代码尚未动手**。本文记录可行性、方案、设置交互、工作量、
> 资源占用与风险，按分期落地。最后更新：2026-11-22。
>
> 已拍板：设置提供「自动 / 固定某一套 / 不显示」三态；自动模式的「启用哪些 + 顺序」
> 收进一个独立弹窗（复选框 + ↑↓ 按钮，不做鼠标拖拽）；关闭模式懒加载、行为等价现状。
> 详见 4.4。

## 1. 背景与目标

有些软件会给文件/文件夹加同步/版本状态角标：Git、SVN（TortoiseGit / TortoiseSVN）、
百度网盘、OneDrive 等。原生资源管理器在主图标左下角叠一个小图标表示状态。

目标：本文件管理器同样显示这些系统注册的角标，**体验与原生一致**——不自己判断
"改没改、同步没同步"，只把系统已有处理器的结果取出来叠上去。

本机实测注册的处理器（`HKLM/HKCU\...\Explorer\ShellIconOverlayIdentifiers`）共 20 来个：

- OneDrive1~7：7 个同步状态；
- Tortoise1~9：9 个版本状态（Normal / Modified / Conflict / Locked / ReadOnly /
  Deleted / Added / Ignored / Unversioned），共用 `TortoiseOverlays.dll` 共享桥接，
  真正状态由安装的 Git/SVN 客户端提供；
- aPipIconOverlay、EnhancedStorageShell、Offline Files 等。

## 2. Windows Overlay 机制（原理）

1. 软件安装后把一个 COM 处理器登记到注册表
   `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Explorer\ShellIconOverlayIdentifiers\<名字>`
   （`HKCU` 同样位置也可），默认值是处理器 CLSID。
2. 资源管理器画完主图标后，按优先级逐个问处理器
   `IShellIconOverlayIdentifier::IsMemberOf(pidl, path)`；命中就用处理器
   `GetOverlayInfo` 提供的小图标叠在主图标左下角。
3. 公开接口：`IShellIconOverlayIdentifier`，自研程序可直接调用。

### 命中与优先级规则（必须与原生一致）

- **每个图标最多叠一个角标**：按优先级依次问，第一个命中的就用，后面不再问；
  不会把多个角标都画上。
- **优先级 = 注册表名称排序**：名字前导空格越多越靠前（原生调顺序的惯例）。
- **系统只取前 15 个**处理器，排在 15 名之后的原生就不生效，程序照搬同样截断。
- 同一家内部的多个状态处理器互斥，只命中当前状态那一个。

### Git + SVN 同目录的行为

目录里同时有 `.git` 和 `.svn` 时，两套处理器的 `IsMemberOf` 都会判定命中自己，
但界面只显示**排序靠前那一套**；显示 Git 还是 SVN 取决于注册表顺序（安装先后、
空格前缀）。这是原生本身的行为，原生资源管理器里同样只出一套角标。程序不自己挑，
照搬优先级即可。技术上可以改成叠两套，但会与原生不一致，不做。

## 3. 现有基础（已核实，可复用）

- 图标架构：主图标直接引用系统图像列表（`SHGetImageList`），按扩展名 / 路径 / PIDL
  取索引；图标缓存在 `src/shell/ShellIcon.{h,cpp}` 的 `IconCache`。
- **已有图标合成先例**：`IconCache::CreateDimmedIcon` / `GetDimmedIconIndex`
  （剪切/隐藏项半透明）。套路是：原图标画进 32 位带 alpha 的 DIB → 处理 →
  `CreateIconIndirect` 转回 HICON → `ImageList_ReplaceIcon` 追加进同一图像列表 →
  按原索引缓存新索引。Overlay 合成复用这套。
- **主列表唯一图标出口**：`FileListView::IconIndexForEntry`（`src/ui/FileListView.cpp`），
  三处消费：自绘小图标、平铺格子、`LVN_GETDISPINFO`。
- `ShellEntry` 已带绝对 PIDL（`pidl`）和 `fullPath`，可直接喂给 `IsMemberOf`。
- 枚举在后台线程（已 `CoInitializeEx`）；图标索引在 UI 线程取。
- 导航栏 `NavigationPane` 单独调 `IconCache`，不走 `IconIndexForEntry`，是第二接入点。

## 4. 方案设计

### 4.1 新增 overlay 管理模块（建议 `src/shell/ShellOverlay.{h,cpp}`）

**A. 处理器注册表（懒加载，按套归并）**

- **懒加载**：不在启动时无条件实例化。只有模式为「自动」或「固定某一套」时才去读
  注册表、实例化处理器；模式为「不显示」时整套不初始化，不读注册表、不加载图标，
  行为与未做本功能前完全一致。
- 读 HKLM / HKCU 两处 `ShellIconOverlayIdentifiers`，按名称排序得到默认优先级；
- 同族处理器归并成**一套**：依据 `InprocServer32` 的 DLL 路径相同 / CLSID 号段相近。
  注意 TortoiseGit 与 TortoiseSVN 共用 `TortoiseOverlays.dll` 桥接，分不到两家，
  合并为一个「Tortoise」项。
- 每个 CLSID `CoCreateInstance` 出 `IShellIconOverlayIdentifier`；
- 调 `GetOverlayInfo` 取 overlay 小图标（HICON 或资源路径），按尺寸缓存；
- 不实现接口、实例化失败的跳过；遵循前 15 个上限；后装的新套默认排末尾。

**B. 条目判定（按模式过滤，按顺序询问，按路径缓存）**

- 判定前先按当前模式确定**启用集合**和**询问顺序**（见 4.4）；
- 在后台枚举线程对每项按顺序依次问 `IsMemberOf(pidl, path)`；
- 第一个命中即记录该套 / 状态标识，存入 `ShellEntry` 新字段 `overlayId`；
- 命中 / 未命中都按路径缓存，避免重复问处理器。

**C. 图标合成**

- 复用 DIB 套路：主图标画满幅，overlay 小图标贴左下角（原生约占主图标 1/4）；
- 合成新 HICON 追加进图像列表；
- 缓存键 = 主图标索引 + `overlayId`，与现有半透明缓存同理。

### 4.2 接入点

- **主列表（第一期 MVP）**：`IconIndexForEntry` 末尾，主索引确定后查 `overlayId`，
  有则合成。
- **导航栏（第二期）**：`NavigationPane` 两处单独接。

### 4.3 线程模型（关键风险点）

- 处理器多为 STA。判定重活放后台枚举线程（已初始化 COM），结果存进 `ShellEntry`；
  UI 线程只按 `overlayId` 合成图标，不碰 COM。
- 不在 UI 线程按需实例化处理器，避免 apartment 问题和卡顿。

### 4.4 设置交互与模式（已拍板）

**三种模式**

| 模式 | 行为 |
|---|---|
| **不显示** | 不初始化处理器、不询问、不合成，图标走原有流程，等价现状 |
| **固定某一套**（如 Tortoise） | 只启用这一套，其它套全部跳过；这套内部状态图标仍由它自己判定 |
| **自动** | 几套都参与，按用户排定的顺序询问，第一个命中的显示 |

**主设置界面（保持现有固定布局，不做内嵌动态列表）**

- 一个**模式下拉框**：自动 / 不显示 / 各套名（选固定某套）；
- 除「自动」外，其余模式直接在下拉里选定即可，主界面不展开任何列表；
- 选「自动」后，弹出一个**独立配置窗口**，在里面设置启用哪些套、各套顺序；
  主界面不内嵌复选框列表，避免动态显隐和重排。

**自动模式配置弹窗（做法 B：↑↓ 按钮，不做鼠标拖拽）**

- 弹窗内一个列表，每项一行：**复选框 + 套名 + ↑ / ↓ 按钮**；
- **复选框**：勾上的套才参与自动判定，没勾的直接跳过；
- **↑↓**：在勾上的套之间调整优先级顺序，第一个命中的显示；
- 同族的多个状态处理器并成一项，不暴露 `OneDrive1`、`Tortoise2Modified`
  这种槽位名；取不到可读产品名时退回注册名；
- 弹窗「确定 / 取消」：确定才落配置，取消丢弃本次改动；
- 触发方式：下拉切到「自动」时弹出该配置窗口；主界面不再单设「配置…」按钮。
  之后想改勾选 / 顺序，把下拉切到别的项再切回「自动」即重新弹出。

**配置字段（`settings.json`）**

- `overlayMode`：`auto` / `off` / `fixed`；
- `overlaySelection`：固定模式下选中的套标识；
- `overlayEnabled`：自动模式下勾上的套标识集合；
- `overlayOrder`：自动模式下各套标识的顺序数组；
- 未记录过的新处理器默认启用、追加到末尾，保证装新软件后角标正常出现。

**说明**

- 下拉/勾选/顺序只管「看哪一套」；具体显示对号还是感叹号，由该套按当前目录状态判定。
- 改完设置重新枚举当前目录、重画即生效；不做主动监听刷新（见 7.5）。

## 5. 缓存与资源占用

| 项 | 策略 | 占用 |
|---|---|---|
| 处理器对象 + overlay 图标 | 全局一份，总共十几个 | 可忽略 |
| 判定结果 | 按路径缓存，生命周期跟当前目录，切目录可清 | 取决于条目数，带上限 |
| 合成图标 | 按「主索引 + overlayId」组合缓存，不重复合成 | 组合数有限 |

**主要成本在判定**：Tortoise / 网盘处理器内部要查 `.git`、同步库等状态，逐项问有开销。
必须只对已枚举 / 可见项判定并缓存，不能后台全量遍历。

**对未同步目录的影响（已评估）**

- 没纳入版本控制 / 同步的目录，也要被各套问一遍才能确认「不归谁管」，这步省不掉；
- 正常处理器对未管理目录快速返回未命中；首次打开有新增询问开销，第二次同目录走
  路径缓存，基本无感；
- 询问放后台线程，不卡界面；处理器出错按未命中兜底；
- 可选优化：目录级粗判——目录里看不到任何版本控制 / 同步标记时整目录跳过询问。
  只能当加速手段，不能当唯一依据（标记位置各家不同，容易漏）；
- 实际耗时取决于第三方处理器质量，条目很多的目录或质量一般的客户端，首次加载
  可能能感觉到慢一点，需第一版跑起来实测。

## 7. 风险与难点

1. **COM 线程模型**：判定放后台 STA 线程，UI 线程不碰 COM（见 4.3）。
2. **第三方处理器质量参差**：个别 `IsMemberOf` 可能卡顿甚至崩。COM 调用靠 HRESULT
   兜底，失败按未命中处理；COM 无原生超时，卡死只能靠隔离进程，MVP 先做异常兜底。
3. **与现有半透明的叠加顺序**：剪切 / 隐藏项先淡化主图标；原生 overlay 不随主图标
   淡化，叠在淡化层之上。顺序需对齐。
4. **三档尺寸**：16 / 32 / 48 都要合成，overlay 位置和比例各调一次。
5. **状态实时刷新**：网盘「同步中 → 完成」、Git 提交后状态变化，缓存要失效重查；
   MVP 先靠切目录 / 手动刷新重建，不做主动监听。
6. **虚拟项**：控制面板等无路径项，处理器一般不覆盖，按 PIDL 问一次即可。

## 8. 分期建议

- **第一期（MVP）**：主列表视图接入，读系统处理器、左下角叠加、按路径缓存；
  导航栏、实时刷新不做。
- **第二期**：导航栏接入、缓存失效刷新、选中 / 淡化叠加细节对齐、异常处理器隔离加固。
