# 图标与缩略图磁盘缓存设计

> 状态：**一期方案已定稿，二期（缩略图）方案已给出；业务代码尚未动手**。最后更新：2026-11-24。
> 本文回答"打开下载文件夹有时候很慢"的原因，并给出只补"磁盘成品"这一层的落地方案。
> 相关背景见 [`docs/进度与状态.md`](进度与状态.md) 顶部「图标磁盘缓存」一节。

## 1. 背景：慢在哪

在本机（2026-11-23/24）实测，结论不是"文件夹太大"——Downloads 只有 29 个条目：

| 测量项 | 结果 |
|---|---|
| 顶层枚举（纯文件系统） | 0.4 ms |
| 程序日志里的枚举完成 | Downloads 29 项 **194～239 ms**；C:\ 15 项 16 ms |
| 磁盘顺序读（276 MB 文件） | 1066 MB/s，队列 0 |
| 首次取图标（全文件夹合计） | **7612 ms** |
| 同一批文件第二次取图标 | 1～14 ms（曾），再次复测又变 6134 ms |

首次取图标最慢的几项：

| 文件 | 大小 | 首次 |
|---|---|---|
| `dsh-latest-windows-x64.exe` | 276 MB | 3829 ms（复测 6134 ms） |
| `Listary.exe` | 12 MB | 1556 ms（复测 1722 ms） |
| 豆包客户端 exe | 882 MB | 892 ms（复测 1100 ms） |
| `TortoiseSVN-*.msi` | 30 MB | 389 ms |

**关键事实：系统侧没有可靠的"取过就不再读"缓存。** 同一批文件几分钟后再查，
`dsh` 从 78 ms 变成 6134 ms——Defender 什么时候重扫，什么时候就是秒级。
而我们的列表**每次重绘都重新问一遍系统**（`GetIconIndexByPidl` 没有缓存），
所以滚动、选中、切窗口都可能撞上整屏卡死。这就是"有时候很慢"的真正机制。

### 1.1 为什么资源管理器不卡

资源管理器有**磁盘上的成品缓存**，它压根不碰这些大文件：

- 位置：`%LOCALAPPDATA%\Microsoft\Windows\Explorer\`
- 分档：`iconcache_16.db` 3 MB、`iconcache_48.db` 11 MB、`iconcache_256.db` 4 MB；
  `thumbcache_*.db` 合计约 8 MB
- 流程：**先查磁盘缓存 → 命中直接用 → 未命中才提取 → 提取完写回**

进程内存里那份只是"当前要画的几个图标"的索引，不是真源；真源在磁盘上，
所以它重启后照样快。我们缺的正是这一层。

## 2. 目标与边界

**目标**：打开目录不再因为取图标而卡；重启程序后也不必重新读一遍大文件。

**不做（已讨论并排除）**：

| 不做的事 | 原因 |
|---|---|
| 按文件体积阈值降级成通用图标 | 实测 Downloads 里 18 个 exe/msi/lnk，**0 个**与通用图标显示结果相同，降级就是显示错误 |
| 按"猜"用通用图标替代 exe | 同上；只有"没有图标资源的 exe"和"目标不可达的 .lnk"结果才一致，前者判定又必须读文件 |
| ~~第一版不做异步~~ → **改为做后台取**（2026-11-24 用户拍板） | 取图标整条挪到后台线程；**没取到就留空，不用占位图标**，取到后只重画那一行；界面线程不再调 SHGetFileInfo |
| 给扩展名图标也落盘 | 实测 28 种扩展名新进程首查共 134 ms、同进程二次 5.9 ms（见 6.2）；落盘收益太小，还要背"关联变更失效"的监听成本 |

### 2.1 分期

| 期 | 范围 | 界线 |
|---|---|---|
| **第一期（本次）** | 图标磁盘缓存（`exe/lnk/ico/scr` 落盘）、统一管线、尺寸数组化、启动空闲预热常用扩展名 | 只碰"图标"：方形、固定尺寸、进图像列表、同步取 |

## 3. 架构：一条管线，两种来源

现在的代码把取图标拆成三个函数各写一套（`GetIconIndex` / `GetIconIndexByFullPath` /
`GetIconIndexByPidl`），缓存也各存一份。合并成一条链：

```
取图标(key)
  ├─ 内存表命中？        → 返回图像列表索引
  ├─ 磁盘缓存命中？      → 读成品位图 → 塞进图像列表 → 记内存 → 返回
  ├─ 都没有 → 取位图（只有这一步分来源）
  │     ├─ 扩展名 / 文件夹：假文件名 + SHGFI_USEFILEATTRIBUTES（不碰文件）
  │     └─ exe / lnk / ico / scr：真实路径或 PIDL（读它自己的资源）
  ├─ 塞进图像列表 → 得到索引 → 记内存
  └─ 该落盘的写磁盘（同时刷新"最后使用时间"）
```

**落盘按来源分**：`ext:`（扩展名/文件夹）不落盘；`file:`（exe/lnk 这类）落盘。

**为什么缓存文件存"像素"而不是"索引"**：现在的图标索引是系统图像列表里的编号，只在本次进程有效
（重启程序编号就变），所以磁盘里必须存像素；命中时把像素做成 HICON、`ImageList_ReplaceIcon(-1)`
追加进图像列表，拿一个新的编号。这条"往列表追加图标"的路径代码里已经在用（半透明图标、角标合成），
不引入新架构。

### 3.1 后台取图标（不留占位图标）

界面线程只做一件事：查内存表。查到就返回编号，查不到就返回**一张全透明的占位图标**的编号
（保留图标位、文字不左移，但屏幕上什么都不显示），同时把这一项丢进请求队列。

- 后台**一个**线程按队列取图：先按来源取（扩展名走假文件名，exe/lnk 走真实路径/PIDL），
  再转成 32 位像素，取完 `PostMessage` 回界面；
- 界面收到：像素 → HICON → 追加进图像列表 → 记内存 → 落盘 → `ListView_RedrawItems` 只重画那一行；
- 切目录 / 换盘：世代号 +1，旧队列整批作废（复用枚举线程已有的写法）；
- 首屏表现：图标"一个个蹦出来"，因为图标位始终占着，行高和文字位置都不跳。

**内存表统一成一张**，key 带前缀避免撞车：

- 扩展名：`ext:.pdf|16`
- 文件：`file:C:\...\a.exe|16|大小|修改时间`

## 4. 磁盘缓存格式

### 4.1 布局

```
%LOCALAPPDATA%\FileExplorer\icons\<哈希前2位>\<哈希>.icn     ← 图标（16/32/48…）
%LOCALAPPDATA%\FileExplorer\thumbs\<哈希前2位>\<哈希>.icn    ← 缩略图（96/128/256…）
```

- 一个资产一个文件，写入用"临时文件 + 改名替换"（原子），**不需要跨进程锁**；
- 按哈希前两位分 256 个子目录，避免单目录文件太多；
- 两个目录分开，天然按种类统计体积和清理（清图标不影响缩略图）。

### 4.2 key

```
key = 种类(icon / thumb)
    + 完整路径（统一小写）
    + 目标文件大小
    + 目标文件修改时间
    + 宽 + 高（像素，来自档位表）
    + 提取版本号（我们换算法/换尺寸策略时 +1）
```

文件名 = key 的 64 位哈希（自实现 FNV-1a/xxHash 类，**不引第三方库**）+ `.icn`。
哈希只用来定位，**真正的 key 存在文件内容里**，命中时逐字段比对，防碰撞。

### 4.3 文件内容

```
[0..3]  "YIC1"（magic，带版本：换格式就变 YIC2，老文件自动废弃）
[4]     种类：0=图标 1=缩略图
[5]     标志位：bit0 = 负缓存（本文件没有可用图像）
[6..7]  宽（uint16）
[8..9]  高（uint16）
[10..11] 保留
[12..]  数据区：key 字符串 + 32 位 BGRA 像素 + 1 位掩码
```

- **负缓存**：缩略图处理器没装、PDF 取不到图这类"必然失败"，记一条 0 字节数据的负缓存，
  避免每次打开都重试；
- **坏档**：magic/尺寸/key 对不上 → 直接删掉该文件重新提取，**绝不影响打开文件夹**。

## 5. LRU 与清理

### 5.1 使用时间怎么记

- 命中时把**缓存文件自身的"修改时间"刷成当前时间**（`SetFileTime` 改 `LastWriteTime`），
  清理按这个时间排序删最旧的；
- **同一个 key 在一次运行里只刷一次**（内存里记标记），避免反复开同一目录时大量元数据写；
- 不重写图标数据，只改一个时间戳字段，几十微秒。

注意：缓存文件名里的哈希用**目标文件**的大小+修改时间（判断文件是否变了）；
缓存文件自身的时间戳只表示**最后使用**。两者不要混。

### 5.2 预算

| 种类 | 单条体积（参考） | 预算 |
|---|---|---|
| 图标 16px | 1.1 KB | 图标合计 **32 MB** |
| 图标 48px | 9.5 KB | 同上 |
| 缩略图 96px | 36 KB | 缩略图合计 **200 MB** |
| 缩略图 256px | 256 KB | 同上 |

### 5.3 触发时机

- 写入新条目时累加体积；超过预算 → 触发一次清扫：枚举该目录 → 按使用时间排序 → 删到 **80%**；
- 清扫放**后台**（或启动后空闲时）做；8000 个文件读属性约 0.5～1 秒，不能挡在打开目录的路径上。

## 6. 尺寸档位（为以后兼容多尺寸和缩略图）

请求尺寸**就近吸附**到最近的档，不让 97px 和 103px 各存一份：

| 档位 | 用途 |
|---|---|
| 16 | 详细信息 / 列表 / 小图标 |
| 32 | 中图标 |
| 48 | 大图标 / 平铺 |
| 96 | 缩略图小格 |
| 128 | 缩略图中格 |
| 256 | 缩略图大格 / 超大图标 |

系统侧现成档位：`SHIL_SMALL`(16) / `SHIL_LARGE`(32) / `SHIL_EXTRALARGE`(48) / `SHIL_JUMBO`(256)；
96 没有现成档，将来要用 `IShellItemImageFactory` / `IExtractIcon` 按像素提取。

### 6.1 对外返回"位图"，不是"图像列表索引"

这是为缩略图留的关键口子：

- 图像列表是**固定尺寸**的（16px 一张、48px 一张），缩略图塞不进去；
- 所以缓存层只返回 `{宽, 高, 32 位像素}`；
- **图标消费者**：转 HICON → 塞进图像列表 → 拿索引（现有机制照旧，`ImageList_ReplaceIcon(-1)`）；
- **缩略图消费者**：直接画 HBITMAP（按比例居中，图片有宽高比）。

### 6.2 扩展名图标为什么不落盘（实测）

2026-11-24 在本机新进程里测了 28 种常见扩展名（`SHGetFileInfo` + 假文件名 +
`SHGFI_USEFILEATTRIBUTES`）：

| 项 | 耗时 |
|---|---|
| 首次全部查完（28 种） | **134 ms** |
| 其中 `.pdf` | 51 ms（要加载 PDF 关联的图标处理程序 DLL） |
| `.iso` / `.pptx` / `.epub` | 5～6 ms |
| 其余（jpg/png/mp4/zip/docx/txt/dll…） | 2～3 ms |
| 同一进程第二次全部查完 | **5.9 ms** |

结论：一个会话里最多多花一两百毫秒，且只在你第一次碰到某类文件时。落盘收益太小，反而要背上
"关联变更失效"的负担——装了新 PDF 阅读器、换默认程序、卸载程序之后，旧缓存必须自动作废，
资源管理器是靠 `SHCNE_ASSOCCHANGED` 通知重建的，我们照做要额外加监听（约 50～80 行）。
不做监听就是"图标换不了"，比慢更糟。

**替代方案（更划算）**：启动后空闲时，后台把常用扩展名（pdf/jpg/png/mp4/zip/docx/xlsx/pptx…）
各查一次，把会话内那张扩展名表填满。约 20～30 行，没有失效问题，收益和落盘接近。

## 8. 验收标准

1. 程序重启后**第二次**打开 Downloads，图标不再读磁盘（日志里"磁盘命中/提取"计数可证）；

## 11. 第二期：图片 / PDF / CDR 缩略图

### 11.1 本机实测（2026-11-24，`IShellItemImageFactory::GetImage`，只认缩略图）

| 文件 | 128px 首次 | 同进程二次 | 换 256px |
|---|---|---|---|
| `4531.jpg`（手机照片） | 成功 128×100，**220 ms** | 5 ms | 成功 256×199，3 ms |
| `4968.png` | 成功 96×128，**163 ms** | 3 ms | 成功 192×256，3 ms |
| `拔尖测评.pdf` | **无缩略图**，20 ms | 4 ms | 同 |
| `备忘_txt.pdf` | 无缩略图，4 ms | 5 ms | 同 |
| `.cdr` / `.ai` / `.psd` | 本机无样本，且未装 Corel/Adobe，注册表里连关联程序都没有 → 取不到 | — | — |

结论：

1. 冷态一张图 160～220 ms（首次要初始化解码器）——**必须异步**，不能在 `LVN_GETDISPINFO` 里同步取；
2. 同进程二次 3～5 ms，且 256 能从已解码结果直接缩，所以按目标尺寸取一次即可，不必先取大再缩；
3. 缩略图**保留宽高比**（128×100、96×128），缓存与绘制都按"方形画布 + 等比居中"处理；
4. PDF/CDR 能不能出图**取决于装了哪个处理程序**：本机 PDF 关联到我们自己的查看器、没有缩略图处理器，
   CDR/AI 没有 Corel → 取不到。二期必须"按能力自适应"，不能按扩展名假定有。

### 11.2 形态：新开一个"缩略图视图"，不引入自绘

- 复用现有 `LVS_ICON` + 固定格子那套（`ViewMode::LargeIcon` 已经这么做），新增 `ViewMode::Thumbnail`，
  格子约 136 px；
- 缩略图**塞进一张专用 128 px 图像列表**（`ILC_COLOR32` 保留透明），沿用"返回索引 → `LVN_GETDISPINFO`
  给 iImage"的现有机制，**不写 owner-draw**；
- 画布 128×128，图片等比缩放居中，空白处填白（透明 PNG 在图像列表里天然带 alpha）。

这是最省的做法：不改列表控件架构，只多一张表 + 一个格子尺寸。

### 11.3 异步与取消

- 只对**可见行**发请求（首行 / 每页条数，滚动时补发）；
- 后台**一个**串行线程按队列取图（并发会让机械盘与 Defender 互相打架）；
- 切目录 / 关窗口 → 世代号 +1，旧队列整批丢弃（复用枚举线程已有的"世代"写法）；
- 取到后 `PostMessage` 回 UI：塞图像列表 → 记内存 → 落盘 → `LVM_REDRAWITEMS` 只重画那一行。

### 11.4 缓存与失效

- key 同 4.2，种类=1（缩略图），宽高=方框边长；预算沿用 200 MB；
- **负缓存带有效期（7 天）**：没有处理程序的格式（本机 PDF/CDR）写负缓存，但不能永久生效——
  图标那条 key 里有目标文件修改时间，装了新程序不会改文件时间，会导致"永远取不到"。
