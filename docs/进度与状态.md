## 图标磁盘缓存（2026-11-24 一期已落地并自测；二期缩略图方案已给出）

> 起因：用户反馈"打开下载文件夹有时候很慢"。查下来不是文件夹大（Downloads 只有 29 项），
> 而是**取图标**：我们的程序每次重绘都重新问系统，系统侧又没有可靠的"取过就不再读"缓存，
> 撞上 Defender 重扫时单个 276 MB 安装包就要 3.8～6.1 秒。资源管理器不卡，是因为它有
> `%LOCALAPPDATA%\Microsoft\Windows\Explorer\iconcache_*.db` 这份**磁盘成品缓存**，压根不碰大文件。
>
> 定案：只补我们缺的"磁盘成品"这一层。**统一取图标管线 + 按需落盘**——
> 扩展名/文件夹图标（实测 28 种新进程首查共 134 ms、同进程二次 5.9 ms）只进内存，不落盘；
> exe/lnk 这类"必须读文件"的落盘。
> 顺手把"每次重绘重复查询"修掉，并把尺寸从"两档布尔"改成按尺寸索引，给以后的缩略图留口子。
>
> 详细设计与实测数据见 [`docs/图标与缩略图缓存设计.md`](图标与缩略图缓存设计.md)。
> 明确不做：按体积阈值降级成通用图标（实测 Downloads 里 18 个 exe/msi/lnk **0 个**与通用图标一致）、
> 第一版异步补齐、扩展名图标落盘。
>

### 1. 处理器用途过滤（黑名单）【已落地 2026-11-23，提交 `08d4890`】

- **要解决的问题**：豆包「操作电脑」在注册表注册了角标处理器 `aPipIconOverlay`（DLL `pip_remote.dll`），配置窗口会把它列成一套「豆包操作电脑」，但它是远程协助 / 影子会话外壳扩展，跟同步状态无关。同类还有 `EnhancedStorageShell`（`EhStorShell.dll`，便携设备加密）和 `Offline Files`（`cscui.dll`，脱机文件）。
- **实现**：`ScanRegistry()` 里加了 `IsBlockedHandler()`，CLSID 表 + DLL 文件名表两道判断，构建 `RawHandler` 时命中就 `continue`。放这里的原因：`EnumerateHandlers()`（判定侧）和 `ListSets()`（配置窗口侧）两个调用点同时生效。
- **落地细节**：
  - CLSID 按 `{61135E38-1A85-4B66-A170-7E764DE2842A}` 忽略大小写比较；DLL 只比文件名（`pip_remote.dll` / `ehstorshell.dll` / `cscui.dll`），不写死路径——豆包装在用户目录下、会随版本换目录。
  - 过滤排在注册名排序之后（早先理由是"不让第 16 位以后补位"，现已不成立——2026-11-23 取消了 15 槽位截断，过滤只是少一项，不涉及补位）。
  - 命中时记一条 `info` 日志，方便日后排查"某套为什么不见了"。
- **实测**：日志出现「角标处理器按用途黑名单跳过：aPipIconOverlay（豆包操作电脑）」，连带原先那条 `0x8007045A`（DLL 初始化例程失败）警告一起消失；枚举数量仍为 14 个（豆包原本就在实例化阶段失败被跳过，现在省掉这一次无用的实例化尝试）。

### 百度网盘「状态」列文字（2026-11-23 评估后不做）

- **现象**：百度网盘同步状态在资源管理器里只出现在详细信息视图的「状态」列（文字），列表/平铺等其它视图则显示在文件名前面；**两个程序都不显示角标**（连原生资源管理器也不显示）。

- **我们能不能做**：能，但要在"文件名前面显示状态文字"（四个视图统一）。代码量评估：

- **拍板：不做**。理由：角标已经把"有没有问题"表达清楚了，状态文字属于锦上添花；而且数据源尚未验证（百度网盘是走云文件 API 还是自写属性都没测），存在"花了 500 行结果读不到值"的风险，不划算。

## 驱动器被隐藏/系统文件过滤误隐藏（2026-11-22）

- 现象：勾选「显示隐藏文件」后，另一台电脑的本地磁盘从「此电脑」消失；本机数据盘正常。
- 根因：枚举第二段磁盘属性补查（`GetFileAttributesW`）对驱动器项同样执行。驱动器路径就是盘根目录 `C:\`，取到的是**根目录**属性；系统盘 / 保留盘、同步映射盘根目录天然带 `FILE_ATTRIBUTE_SYSTEM`（常同时带 HIDDEN）位，于是驱动器被误标成系统文件。按规则系统文件只受「显示系统文件」开关管，只开「显示隐藏文件」时即被过滤。
- 实测（复刻程序规则枚举此电脑）：本机 `C:\`、`V:\` 根目录 0x16（Hidden+System+Directory）会被第二段判为隐藏；`D/X/Y/Z` 不带 SYSTEM 保留。第一段 SFGAO 对各盘均不报 HIDDEN/SYSTEM，问题只在第二段。
- 修法：第二段补查前用 `DriveLetterFromParsingName(fullPath)` 识别驱动器项，驱动器豁免该段——不读根目录属性、不置隐藏/系统标记、不过滤，始终保留；与资源管理器此电脑行为一致。其它目录的普通文件夹/文件判定不变。
- 遗留：第一段 SFGAO 过滤未对驱动器豁免（实测 Shell 不给驱动器报 HIDDEN/SYSTEM 位）；若日后遇到某盘被第一段隐藏再补。
- 验证：规则回归 400 条 0 不一致；e2e 主窗口全过；Release/Debug x64 编译通过；settings.json 已备份还原。**驱动器在两开关下的实际显示待用户实机确认。**

## 主文件夹系统项判定收窄（2026-11-22）

- 现象：主文件夹（Home）里开发目录 `C:\git\explorer\bin\x64\Debug` 排到第 1 位，git 文件、dist 安装包、Z: 网络盘、AppData 工作区截图等真实磁盘路径，和真正的系统入口混在同一组。
- 根因：`IsDesktopSystemItem` 兜底过宽——空路径 / `::` 解析名 / 桌面目录本身之外，**其余所有真实磁盘路径一律 `return true` 算系统项**。比较器先按系统项分组、组内再分文件夹/文件，这些普通路径被抬到了系统项一侧。
- 修法（方案 A，仅收窄判定，不动文件夹/文件归类）：兜底改为先用 `shell::KnownFolderDisplayName` 精确匹配 6 个已知系统目录入口（桌面/下载/文档/图片/音乐/视频）本身，命中才算系统项；其它真实磁盘路径一律 `return false` 按普通项处理。
- 不动：`isFolder`/压缩包纠偏、排序比较器、排序菜单与状态持久化；Home 页剪切/删除保护本就走 `KnownFolderDisplayName`，不依赖 `isSystemItem`，未受影响。
- 预期（升序）：系统项段 = 虚拟项 + 6 个系统目录入口；普通文件夹段 = Debug、桌面子文件夹、网络盘、压缩包；文件段按名称。降序镜像逻辑不变。
- 遗留边界：网络盘/属性取不到的压缩包可能残留 `isFolder=true`（本次按方案 A 未加固，扩展名命中即按文件的改法留待后续）。

## 决定：Edge/Chrome「打开文件夹」20 秒不再修（2026-11-20）

**根因**：Chromium（Chrome/Edge 共用）的 `ShowItemInFolder` 调
`SHOpenFolderAndSelectItems`；默认文件管理器不是 Explorer 时，Windows 会等一个
**真实 Shell 窗口**，20 秒后返回 `E_ABORT`，Chromium 再回退 `ShellExecute` 启动我们。

实测与排除：

- `SHOpenFolderAndSelectItems(目录/文件, 0, NULL, 0)` 固定 **20.0–20.5 秒**；
  文件 pidl、目录 pidl 都一样；
- 进程在 20 秒后才启动；关掉 Yexplorer 也慢，只有重启浏览器恢复（状态缓存在浏览器进程）；
- 注册 `IShellWindows`、`LocationName` 改显示名、`LocationURL` 补结尾斜杠、改 `explore`
  动词、`ShellExecuteEx + IDLIST`，均无效或本来就是快的；
- 隐藏 Explorer 壳可以解决，但**决定不采用**；Chrome/Edge 扩展 + Native Messaging
  只是新增入口，也不能修系统按钮。

**结论：接受这个入口的 20 秒，不再投入。** 以后不要再重复尝试隐藏 Explorer、注册
Shell 窗口、LocationName/URL 调整、DDE、改 explore 动词。

**定位**：应用日志里两次都是 **4ms 完成转发**（「该目录已有窗口，本次启动交给它」），

**修复**（`ui/WindowRelay` + `MainWindow::ActivateFromRelay`）：

- 新增 `ui::ForceForegroundWindow()`：最小化先 `SW_RESTORE`，再临时
  `AttachThreadInput` 到当前前台线程，然后 `SetForegroundWindow` + `BringWindowToTop`，
  最后解挂；返回是否真的成了前台。
- 转发进程（由前台程序启动的那个）在收到成功回复后也补一次置前，并记录
  「抢前台授权=有/无，最终前台=是/否」。
- 接收方 `ActivateFromRelay` 改走同一个函数，日志记录置前是否成功。

**实测**：记事本在前台时触发第二次打开，10ms 内 Yexplorer 变成前台；
日志 `抢前台授权=有，最终前台=是`。

## 结论：Edge/Chrome/WPS 的「选中文件」无法被本程序接管（2026-11-20 实测）

**实测方法**：给自动化对象加上 QI / Invoke / vtable 日志，开关打开，调用
`SHOpenFolderAndSelectItems(目录, 文件)`。

**结果**：整个调用期间，我们的对象**只收到一次 IDispatch 的 QI（注册时）**；
没有 `Invoke`、没有 `get_LocationURL` / `get_HWND` 的 vtable 调用，随后直接返回 `E_ABORT`。

**结论**：

- Windows 的 `SHOpenFolderAndSelectItems` 只对 **Explorer 自己进程内的 shell 视图**
  （`IShellBrowser` / `IShellView`）下发选中；
- `IShellBrowser` / `IShellView` 是自定义接口，跨进程没有代理/桩，ShellWindows 服务
  也不会调用第三方窗口上的这些接口；
- 所以即使把 `IServiceProvider` / `IShellBrowser` / `IShellView` 全实现一遍，
  跨进程也接不到这个请求。这是"替换 Explorer"类工具在这个 API 上的固有限制
  （StackOverflow 上 xplorer2 作者也得出同样结论）。
- 因此 Edge/Chrome/WPS 的「打开文件夹」**只能打开目录、无法选中文件**；
  想让它们选中，只能靠调用方自己传 `/select,<文件>`（微信/部分打印软件那样，已支持）。

**补做的实验（也失败）**：临时把主窗口类名改成资源管理器的 `CabinetWClass`
（怀疑 API 按窗口类名过滤），重新调用仍然 `E_ABORT`、自动化对象依然没有被调用。
说明过滤点不只在窗口类名，跨进程 shell 视图这条链路整体不可达。

**保留的部分**：`IShellWindows` 注册（设置里默认关）仍能让 `Shell.Application`
这类工具读到 Yexplorer 的当前目录（实测 `Name/LocationURL/HWND` 正确）；
Listary 走的是**插件**（上一节），和这条无关。

## 修复：explorer 代理不认 Chromium/Electron 的 file URL（2026-11-20）

**现象**：在 DeepSeek Harness 文件面板点右上角箭头（「显示文件位置」）打开的是系统资源管理器，

**原因**（查 `app.asar` 得到其真实调用）：

- DSH 的 reveal 执行的是 `explorer.exe "/select," "file:///C:/git/explorer"`；
- 代理原来只认两种写法：`/select,C:\path`（路径在同一参数里）或 `/select`（7 字符）+ 下一个参数；
  **不认 `/select,`（8 字符，逗号后为空）单独一个参数**；
- 而且路径是 `file:///` URL（正斜杠、`%2C`/`%3D` 编码），`GetFileAttributesW` 也不认；
- 于是命中“看不懂就直通系统”的安全阀，交给真正的 `C:\Windows\explorer.exe`。

**修复**（`src/launcher/ExplorerLauncher.cpp`）：

- 新增 `FileUrlToPath()`：`file:///C:/...` → `C:\...`；`file://server/share` → `\\server\share`；
  百分号解码（`%20`/`%2C`/非 ASCII 的 UTF-8 字节）；`/` 统一转 `\`；
- 解析新增两条：`/select,` 单独参数时取下一个参数当路径；裸 `file:` URL 也直接当路径；
- launcher 版本 `1.0.0.1` → `1.0.0.2`；`res/explorer-proxy-x64.exe` 已刷新，主程序已重编内嵌。

**验证**：

- 直接调代理的五种写法全部命中本程序：`/select,` + URL、`/select,C:\...`、纯 `file:///...`、
  裸路径、含逗号路径（`%2C` 正确解码为 `,`）；

## 临时缓存修复 P1~P8（2026-11-20）

第三方重构（`3c67cf6` 前后）把解压/缓存搬到 `src/shell/ContainerExtract.cpp` 时把旧逻辑
原样搬了过来，连带搬进了几个 bug。这次逐条修掉（都不改变对外行为，只是让缓存"该清的能清掉、
不该清的别误删"）：

- **P1 半成品永远清不掉**：zip 通道的半成品叫 `正式名.yexp-partial.<pid>.<序号>`，
  判据却按"名字以 `.yexp-partial.` 开头"，永远匹配不上 → 改成"名字里含该标记"。
- **P2 每个窗口都起一条清理线程**：清理原本写在主窗口 `OnCreate` 里，开几个窗口就重复扫、
  并发删、日志重复 → 改成 `std::call_once`，整个进程只跑一次（依旧后台线程，不阻塞启动）。
- **P3 清理递归整棵缓存树**：为了找一个过期缓存会把没超期的目录整个走一遍 → 加"条目数
  30000 + 500ms"双预算，超了立刻收手，剩下的下次启动接着清（`CleanupBudget`）。
- **P4 落地目录不看时间、也不管谁在用**：`_yexp_landing_*` 原先任意层级见到就删，
  可能删掉另一个实例正在写的中间物 → 现在同样受"7 天"约束，并且从名字里解析属主进程号，
  `OpenProcess` 判活；判活失败/拿不准一律按"活着"处理（宁可少删一次）。
- **P5 超长路径失败**：临时路径 = 临时根 + 包内路径，很容易越过 260 → 解压/清理链路统一套
  `pathutil::MakeLongPath`（`\\?\`）。另把 rar/7z 通道的落地目录从 outputPath 的父目录
  上提到**缓存根**：这条通道走 Shell.Application 的 `CopyHere`，不认 `\\?\`，
  只能靠缩短路径来兜住。包内单个文件名本身超长的情况仍有上限（COM 侧无解）。
- **P6 缓存目录时间不刷新**：包里有顶层文件夹时，后续解压写的是更深一层，缓存目录本身的
  `ftLastWriteTime` 不动 → 7 天到期会把刚用过的缓存当旧货删掉。现在解压成功后
  `RefreshTempDirectoryTime()` 把缓存目录的写入时间刷新成"现在"（命中缓存不刷新）。
- **P7 0 字节文件永远判不成缓存**：判据里把"实际 0 字节"一律当未写完 → 改成只有
  "包声明了大小但实际不符"才算坏；声明 0 字节的文件只看时间戳。
- **P8 `TempDirectoryFor` 重复取临时根**：自己又调一遍 `GetTempPathW` 拼路径，
  和 `TempRoot()` 两份实现容易走偏 → 改为复用 `TempRoot()`。

验证：Release / Debug x64 均 0 错误 0 警告；`tools/run-tests.ps1` 批量重命名回归 400/400。
启动清理与解压链路的实测（双击压缩包、多窗口、超期缓存）留给人工验证。

## 修复：配置保存并发写坏（2026-11-19）

**现象**：`%APPDATA%\FileExplorer\settings.json` 被写坏，程序加载时判坏并改名成
`settings.json.bad`，随后用默认值继续跑，用户丢了 4 条固定项和十几个扩展名账本。

**原因**：多开几个窗口时，几个实例可能同时 `Settings::Save()`。它们都写同一个

## 本轮追加（2026-11-18）：压缩包拖放收尾 + 拖动提示条改自绘图标

### ① 拖动提示条（光标右下角「复制到 / 移动到 / 链接到 / 不能放到」）

  | 符号 | 用在 | 大小 | 边缘 |

  | 加号 | 复制 / 添加到 | 12px | 半透明抗锯齿 |

  理由：16px 的箭头硬边更利落；12px 的圆环和 2px 细线用硬边会碎成台阶（详见坑 38）。

- 代码全在 `src/shell/ShellDragDrop.cpp`：常量区（`kDropTipHeight` / `kDropTipSymbolSizeDot` /

- 现象：拖文件夹 A 放到 A 自己身上、或放进 A 里的子文件夹，原来能通过所有检查，
  最后由 `IFileOperation` 报「不能把文件夹移到自身或子文件夹」，而且**系统自己弹错误框**（详见坑 35）。
- 现在：拖动阶段就判死——`shell::IsSelfOrDescendantPath` 判断，复制和移动一律返回"不可放置"，

- 原来拖出的权限清单只有 `COPY | MOVE`，按 Alt 时任何目标返回"链接"都被系统判为不允许，
  → 拖到哪都是禁止光标（详见坑 36）。
- 现在普通项给 `COPY | MOVE | LINK`；从压缩包解出的临时副本仍只给 `COPY`

- 已知代价：给外部程序声明 LINK 后，个别目标在不按修饰键时可能把默认效果判成复制（坑 19 记过这个现象）。
  11-18 实测同盘拖到本程序窗口仍是"移动"，**跨程序尚未复验**。

### ④ 明确保留现状、不再改的

- 同目录按 Alt 建快捷方式：执行前会被「同目录剔除」规则清掉

  "拖放的源和目标是同一个目录（移动对自己没意义），忽略"。用户确认保持现状。
- 压缩包第 3 步（zip 内部的剪切 / 删除 / 属性菜单）仍未做，现在只有「打开 / 复制」。

### 阶段 5：文件操作改后台执行 + 右键菜单

**一、大文件复制不再卡界面**

- 关闭窗口时会等后台操作收尾（用户也可以在进度框里点取消让它提前结束）

### 阶段 7：剪贴板与系统互通

**原来什么毛病**：剪贴板只记在自己程序内存里。
从资源管理器复制的文件，在本程序按 Ctrl+V 粘不进来；
在本程序复制的文件，到资源管理器里也粘不出来。

**现在怎么做**：改用 Windows 的标准剪贴板格式。

| 格式 | 作用 |
|---|---|
| `CF_HDROP` | 一堆文件路径。资源管理器、桌面、别的程序都认这个格式 |
| `Preferred DropEffect` | 一个数字：1 = 复制，2 = 剪切。没有它接收方一律当复制处理，Ctrl+X 就失效 |

- Ctrl+C 往剪贴板写 `CF_HDROP` + 效果 1（复制）
- Ctrl+X 往剪贴板写 `CF_HDROP` + 效果 2（剪切）
- Ctrl+V **每次都从系统剪贴板读**（不是读自己内存里记的），所以从哪儿复制来的都能粘
- 剪切粘贴成功后把剪贴板清空（和资源管理器行为一致）

**几个容易翻车的细节**：

1. `SetClipboardData` 成功之后，那块内存就归系统了，**绝对不能再 `GlobalFree`**，
   否则程序直接崩。只有失败时才需要自己释放。
2. `GetClipboardData` 拿到的内存只有到 `CloseClipboard` 之前有效，
   所有字符串必须在关闭剪贴板之前复制出来。
3. 剪贴板同一时间只能被一个程序占用，遇到占用要重试（我们重试 10 次，每次隔 50ms）。

### 阶段 8：你提的三个问题（已全部实测通过）

**问题 1：被剪切的文件要变色（和资源管理器一样）**

做法分两半：

| 部分 | 做法 |
|---|---|
| 图标变淡 | `IconCache::GetDimmedIconIndex`：把原图标用 32 位 DIB 重画一遍，逐像素把 alpha 减半（等于 50% 透明），再用 `CreateIconIndirect` 变回 HICON，追加进图标列表并缓存 |
| 文字变灰 | 列表 `NM_CUSTOMDRAW`：`CDDS_PREPAINT` 返回 `CDRF_NOTIFYITEMDRAW`，`CDDS_ITEMPREPAINT` 把 `clrText` 设成 `RGB(150,150,150)` 并返回 `CDRF_NEWFONT` |

实测：未选中时灰字 + 淡图标都清楚；选中状态下文字走系统高亮（白字），图标仍然淡。

**问题 2：文件被剪切走了，源目录还显示着它**

移动完成后遍历本次操作涉及的路径，凡是父目录等于当前目录的，直接从列表里摘掉
（`RemoveItemByPath`），不重扫。

实测：本来的场景（剪切 → 进子目录 → 粘贴 → 回源目录）其实不会残留，
这条属于保险性修复，一并做了。

**问题 3：删除、复制会整表刷新，新建文件夹又不刷新——统一成"不整表刷新"**

核心是 `FileListView::MergeResult`：拿到新枚举结果后，逐行比对 `fullPath`，
找到第一个不同的位置 `common`：

- 全等 → 直接返回，一个像素都不重绘
- 有差异 → `SetItemCountEx` 新数量 → 还原选中和滚动 → `ListView_RedrawItems(common, count-1)`

另外两处必须同时改，否则会"先空再满"：

1. `StartEnumeration` 不再无条件 `SetResult(nullptr)`，只有**目标目录 ≠ 当前显示目录**时才清空
2. `RestoreSelectionAndScroll` 先 `LVM_SETITEMSTATE(-1, 0)` 清空所有选中再按名字恢复
   （否则"选中的行号"会粘到新内容上，等于选错了东西）

粘贴完成后用 `AllPaths()` 求差集 + `SelectPaths()` 把新出现的项选中，和资源管理器一致。

`OnEnumerationDone` 和 `OnColumnClick` 都改成走 `MergeResult`。

```
DWORD ComputeDropEffect(键盘状态, 源声明的效果, 是否同盘)      // 算效果
bool  IsSameDrive(路径A, 路径B)
```

**结构**：拖出侧是"数据对象 + 拖动源"（数据对象优先用系统标准壳对象
`SHCreateDataObject`，造不出来才用自己拼的 `CF_HDROP` 简易对象）；
接收侧是 `IDropTarget`，列表和左栏各注册一个。

**这一块踩了六个坑，都记在踩坑记录里了**（坑 14～坑 19）：
`DROPEFFECT` 没有类型、拖放回调的坐标是屏幕坐标、左栏命中要认整行、
数据对象不能立刻销毁、只给 `CF_HDROP` 会导致"成功但没落地"、
allowed 里带 LINK 会改变对方的默认效果。

### 阶段 9.5：拖到子文件夹 + 外部改动自动刷新（你提的两个问题）

**问题 1：拖到列表里"新建文件夹"这种文件夹上没反应**

原来列表的落点永远是"当前目录"，拖到文件夹图标上也不会进那个文件夹。

改成两级判断：

1. 鼠标压在这一行上（整行都算，压在其他列上也认），**且这一行是文件夹** →
   落点 = 这个文件夹的完整路径
2. 压在文件行上 / 压空白处 → 落点 = 当前目录

视觉反馈：用系统自带的拖放高亮（`LVIS_DROPHILITED`）把鼠标正压着的那一行点亮，
和资源管理器一致；鼠标离开列表或放完自动清掉。

**问题 2：文件被移走 / 删除后列表不自己更新（本程序内部、资源管理器外部都不刷）**

根因：以前只有"本程序自己做文件操作"结束时才刷新一次，
别的程序动过的文件，本程序完全不知道。

新增 `src/core/FolderWatcher.*`：用系统的 `ReadDirectoryChangesW`
盯着当前目录，一有变化就通知主窗口。

三道保护，保证它不会拖慢速度、也不会打断用户：

| 保护 | 做法 | 解决什么 |
|---|---|---|
| 独立线程等待 | 监视放后台线程，没变化时完全睡着，不占 CPU | 不在界面线程做阻塞调用，窗口不卡 |
| 通知合并（防抖） | 收到通知只排一个 250ms 定时器，反复重置；动静停了才真正刷一次 | 批量复制一万个文件时不会把界面刷成幻灯片 |
| 冲突退让 | 文件操作进行中 / 正在 F2 改名，这一轮直接跳过 | 刷新不会打断正在进行的操作和输入 |

刷新本身走的是已有的**差异更新**路径（`MergeResult`），
只重绘真正变了的那几行，不会整表重建。

### 3. 控制面板项双击打不开（已修复，实测通过）
根因有两层：
1. 这类项的解析名是「父项 + \0\ + 显示名」（如 `::{26EE0668-…}\0\字体`），
   **Shell 自己解析不回来**（`SHCreateItemFromParsingName` 失败、

2. 换成 `IShellItem → BHID_SFUIObject → IContextMenu → InvokeCommand` 也不行：
   实测菜单能查出 45 项，但不管用 `"open"` 还是用第一项序号调用，
   都回 `E_INVALIDARG(0x80070057)`。

改法：**把枚举时的绝对 PIDL 存进 ShellEntry**（纯字节，不含 COM 指针，符合跨线程约定），
打开时用 `ShellExecuteExW` + `SEE_MASK_IDLIST | SEE_MASK_INVOKEIDLIST` 执行默认动词。
- `ShellEntry` 新增 `std::vector<unsigned char> pidl`，只在 Shell 命名空间目录里填
  （物理目录的条目用 fullPath 就够，省掉每项一次 PIDL 拼接）。
- 新增 `shell::OpenShellItemByPidl(HWND, pidlBytes)`；
  `MainWnd::OnItemActivated` 两个分支都改成「先 PIDL → 再路径字符串 → 最后 ShellExecuteW」。
- 实测：双击「字体」打开系统「设置」；双击「恢复」弹出控制面板恢复页；
  双击「程序和功能」正常进入其 33 项列表。
- 未实测：BitLocker（可能触发 UAC）、「设备和打印机」里的具体打印机（会触发真实设备操作），

### 7. 「主文件夹」排序：系统项在前、桌面上的东西在后

现象：主文件夹（顶层桌面，51 项）原来全部按名字混排，
「此电脑」「回收站」「控制面板」「库」这些散落在一堆桌面文件中间。

改法：
1. `ShellEntry` 加 `isSystemItem`，枚举时由 `IsDesktopSystemItem` 判定：
   - 路径为空、或形如 `::{GUID}` → 系统项（虚拟项）
   - 路径落在桌面目录 / 公用桌面目录「之下」→ 桌面上的东西
   - 路径正好等于桌面目录本身（即「桌面」这个系统入口）→ 系统项
   - 其余（驱动器、用户目录、OneDrive、KnownFolder 入口）→ 系统项
   桌面目录用 `FOLDERID_Desktop` / `FOLDERID_PublicDesktop` 现查并缓存，
   用户把桌面搬到别处也能判对。
2. `CompareEntries` 最前面加一条：`isSystemItem` 不同时，系统项在前。
   这一条不受"点哪一列排序"影响，其余规则（文件夹优先 → 列 → 名字）不变。

实测：17 个系统项在前（DVD 驱动器、M W、OneDrive、此电脑、回收站、控制面板、库、视频、
图库、图片、网络、文档、下载、音乐、主文件夹、桌面），34 个桌面项在后，
组内仍是文件夹优先 + `StrCmpLogicalW` 名称序。

**8.2 从「主文件夹」点进「文档」，地址栏写「文档」、向上回「主文件夹」**

系统资源管理器记的是"从哪儿点进来的"，不是纯路径。照这个做：

1. `MainWindow` 加 `m_navOrigins`（小写路径 → { 显示名, 上一级 }）。

2. 地址栏/标题统一走 `DisplayNameFor(path)`：有来源记录就用记录的名字，否则按路径推导。
3. `AddressBar::SetPathWithLabel` 加第三个参数 `wholeLabel`：名字和路径不一样时，

   点击它照旧跳到该路径。

   否则名字刚设上就被清掉（踩了一次）。
4. `GoUp` 先查来源表：有记录就回记录的上一级，没有才走 `shell::GetParentPath`。

### 11. 阶段 10：窗口状态持久化（记住上次的样子）

以前每次打开都是"居中 1180x740、左栏 240、默认视图、从 C:\ 开始"，
用起来每次都要重新拖一遍。这一版把这五样记进配置文件，关掉再开还是原样。

记什么（都写在 `%APPDATA%\FileExplorer\settings.json`，和"固定区"同一个文件）：
```json
{
  "window":    { "x": 100, "y": 80, "width": 1000, "height": 700, "maximized": false },
  "paneWidth": 300,
  "columns":   { "time": 160, "type": 120, "size": 110 },
  "view":      { "mode": 0, "manual": true },
  "lastFolder": "C:\\Users\\user\\Documents"
}
```
- `window`：还原后的窗口位置与大小，`maximized` 记"关的时候是不是最大化"。
- `paneWidth`：左栏有多宽（拖中间那条竖线得到的值）。
- `columns`：详细信息视图里"修改日期 / 类型 / 大小"三列的宽度（文件名列是自适应的，不用记）。
- `view`：`mode` 是查看模式编号（0 大图标 / 1 小图标 / 2 列表 / 3 详细信息 / 4 平铺），
  `manual` 表示"这是用户从「查看」菜单亲手选的"。只有亲手选过的才一直沿用；
  没选过的话仍然按目录类型自动定（此电脑=平铺，主文件夹=小图标，普通目录=详细信息）。
- `lastFolder`：关窗口时停在哪个目录，下次直接打开它。

什么时候写：
- 关窗口（`WM_CLOSE`）—— 窗口位置大小、当前目录、查看模式；
- 拖完左栏分隔线松手 —— 左栏宽度；
- 拖完表头列宽松手（`HDN_ENDTRACK`）—— 三列宽度。

怎么恢复（`MainWindow::RestoreSavedLayout()`，在 `WM_CREATE` 里调）：
1. 左栏宽度 → 直接设 `m_navWidth`；
2. 三列宽度 → `FileListView::SetFixedColumnWidths(...)`；
3. 查看模式 → 用户选过就先套上，等导航完再按目录规则走。

窗口位置比较特殊：必须**在建窗口之前**读（`Create()` 里 `Settings::Load()`），
按记下来的矩形建窗，否则会先以默认位置开一下再跳。两条保护：
- 记下来的矩形如果已经不在任何显示器上（换了分辨率、拔了外接屏），回居中开窗，并在日志里说明；
- 记下来的目录如果没了（删了、U 盘拔了、虚拟项解析不出来），回 `C:\`，同样写日志。

实测（窗口 100,80 1000x700、左栏 300、大图标、进「文档」、关窗口再开）：
配置写入了上面那一整组；重启后标题「文件管理器 - C:\Users\user\Documents（5 项）」，

## 阶段 12（进行中）：打开方式 —— 自研账本，不被任何第三方程序劫持

### 需求口径（用户逐条敲定的）

- 右键「打开方式」二级菜单**只读我们自己的账本**，弹出时零注册表读取、零文件探测。
- 某个扩展名**第一次**双击 / 右键「打开」时弹一次设置窗口，让用户定默认程序，之后固化。
- 账本列表是**快照式**：只在"打开设置窗口"那一刻从系统拉候选，平时不自动更新；
  新出现的程序默认勾选，用户可以取消，取消状态永久保存。
- 商店应用（UWP / 打包桌面应用）必须能打开。
- 默认程序被卸载 → 弹窗让用户重选；菜单里非默认的程序被卸载 → **直接消失，不标灰**。
- 特殊类型（exe / lnk / bat / cmd / msi / scr / ps1 等）和文件夹不接管。

### 只在两个时机读系统（用户明确否决了"右键菜单弹出时探测"）

- C：打开设置窗口时 —— `EnumerateCandidates` + `ProbeAll`，结果写进配置的 `alive` 字段。
- D：真正打开文件时 —— 打开前再 `IsAvailable` 验一次。
- 右键菜单只读内存里的 `alive`：`-1` 未知照常显示、`1` 在、`0` 直接跳过。

### 数据落盘（settings.json 新增 openWith 节点）

```json
"openWith": {
  ".txt": {
    "default": "uwp:Microsoft.WindowsNotepad_8wekyb3d8bbwe!App",
    "items": [
      { "kind": "uwp", "appId": "Microsoft.WindowsNotepad_8wekyb3d8bbwe!App",
        "progId": "AppX4ztfk9wxr86nxmzzq47px0nh0e58b8fw",
        "name": "记事本", "enabled": true, "alive": 1 },
      { "kind": "exe", "path": "C:\\…\\WINWORD.EXE", "args": "", "name": "WINWORD.EXE",
        "enabled": true, "alive": 1 }
    ]
  }
}
```

身份串 `OpenWithKey`：exe 用 towlower 的全路径，商店应用用 `"uwp:" + AUMID`，
勾选状态和默认程序都按这个串比对，程序换版本目录不会张冠李戴。

### 两套启动路径

- **Win32**：`CreateProcessW`，参数按模板拼（先替换带引号的 `"%1"`，再替换裸 `%1`；
  `--single-argument` 系列不加引号且转正斜杠；浏览器家族转正斜杠），工作目录 = exe 目录。
- **商店应用**：`ShellExecuteExW`，`fMask = SEE_MASK_CLASSNAME`，`lpClass = 该 ProgID`。
  系统会按 `HKCR\<ProgID>\shell\open\command` 里登记的 `DelegateExecute` 去激活。
  因为 `lpClass` 是我们自己账本里的 ProgID、不是留空，所以系统"当前默认关联"改成什么
  都影响不到——这仍然是不被劫持的。

### 右键「新建」二级菜单

清单来源和资源管理器一致：`HKCU\Software\Microsoft\Windows\CurrentVersion\Explorer\
Discardable\PostSetup\ShellNew` 的 `Classes` 值（REG_MULTI_SZ）给顺序，
每行再去三级注册表视图找模板：

1. `HKCR\<行>\ShellNew`（64 位）
2. `HKCU\Software\Classes\<行>\ShellNew`
3. `HKCR\Wow6432Node\<行>\ShellNew`（32 位程序，如 WinRAR/WPS）

模板类型：`Directory`（文件夹）、`NullFile`/`Data`（空文件）、`FileName`（复制模板）、
`Command`（外部程序自己建，`%1` 换成目标目录）。

本机枚举 15 项，文字与顺序与系统菜单逐字一致：

| 次序 | 显示名 | 键 | 类型 |
| --- | --- | --- | --- |
| 1 | 文件夹 | Folder | Directory |
| 2 | 快捷方式 | .lnk | NullFile+Handler → 系统向导 |
| 3 | BMP 图像 | .bmp | NullFile（系统内置项） |
| 4 | DOC 文档 | .doc | NullFile（注册表已无模板，兜底） |
| 5 | DOCX 文档 | .docx | NullFile（兜底） |
| 6 | WPS PDF 文档 | .pdfwpsshellnew | Command |
| 7 | PPT 演示文稿 | .ppt | NullFile（兜底） |
| 8 | PPTX 演示文稿 | .pptx | NullFile（兜底） |
| 9 | WPS AI 生成 PPT | .pptxwpsaicreateshellnew | Command |
| 10 | WinRAR 压缩文件 | .rar | FileName |
| 11 | RTF 文件 | .rtf | NullFile（兜底） |
| 12 | 文本文档 | .txt | NullFile（系统内置项） |
| 13 | XLS 工作表 | .xls | NullFile（兜底） |
| 14 | XLSX 工作表 | .xlsx | NullFile（兜底） |
| 15 | WinRAR ZIP 压缩文件 | .zip | FileName |

规则细节：

- 排序：文件夹、快捷方式固定前二，其余按扩展名字母序（系统就是这么排的）。
- 显示名优先级：`MenuText`（`SHLoadIndirectString` 解析 `@shell32.dll,-30318`）→
  ShellNew 默认值 → 扩展名登记的 ProgID 的友好类型名（`AssocQueryString`）→
  按扩展名问系统 → 系统类型名 → 键名。
- 图标优先级：`IconPath`（`SHDefExtractIconW` 取 16px）→ 模板文件图标 →
  系统文件夹图标 → 扩展名图标 → ProgID 的 `DefaultIcon`。
- 过滤：处理器缺失的项（`.library-ms`）、命令里的程序已不存在的项（`.contact` 指向
  已卸载的 `Wab.exe`）不显示，系统菜单同样不显示它们。
- 「快捷方式」：`.lnk` 的 ShellNew 是 Handler + NullFile，直接建空文件是坏文件，
  改为走系统自己的「新建快捷方式」向导：拿目录背景的 `IShellFolder` →
  `IContextMenu` → `QueryContextMenu` → `IContextMenu2::HandleMenuMsg(WM_INITMENUPOPUP)`
  填充「新建」子菜单 → 找到「快捷方式」那一项的命令号 → `InvokeCommand`。
  （`rundll32.exe appwiz.cpl,NewLinkHere` 在 Win10 实测无效，进程启动即退出。）
- 建完立刻 `InsertEntry` + 选中 + 进入改名；向导类创建完刷新目录。
- 一级菜单里另有「新建文件夹」（原来就有，保留），放在「新建」子菜单上方；
  新建后同样自动进入重命名。
- 清单在启动后由后台线程枚举一次，存内存；新装软件需重启程序才出现。

## 阶段 14：右键菜单按场景拆分（2026-11-15）

以前只有一套菜单，靠"有没有选中"给项置灰，结果空白处和文件/文件夹/多选
共用同一套：文件右键也出现「新建」、多选里还留着「重命名」、盘符能被重命名。

这一版先把场景判出来，再按场景拼菜单。判定只用内存里的条目数据
（`isFolder` / 路径前缀 `::` `shell:` / 选中数量 / 是不是根目录），
不读注册表、不调 COM、不探测文件，右键弹出仍然零成本。

| 场景 | 什么时候 | 菜单项 |
| --- | --- | --- |
| 空白处 | 没选中任何项 | 查看 / 粘贴（剪贴板有文件才出现）/ 新建文件夹 / 新建 / 刷新 / 属性 |
| 单文件 | 只选中一个普通文件 | 打开 / 打开方式（账本里有程序才出现）/ 剪切 / 复制 / 删除 / 重命名 / 属性 |
| 单文件夹 | 只选中一个文件夹 | 打开 / 在新窗口中打开 / 剪切 / 复制 / 删除 / 重命名 / 属性 |
| 多选 | 选中 2 个以上 | 打开 / 剪切 / 复制 / 删除 / 属性 |
| 盘符或虚拟项 | 盘符根目录、`::`、`shell:` 项 | 打开 / 在新窗口中打开 / 属性 |
| 组标题 / 分隔行 | 点在这两种行上 | 不弹菜单 |

分隔线分组照资源管理器：空白处是「查看 ┃ 粘贴 ┃ 新建 ┃ 刷新 ┃ 属性」，
单文件是「打开、打开方式 ┃ 剪切、复制 ┃ 删除 ┃ 重命名 ┃ 属性」。

按用户要求去掉的项：「创建快捷方式」「发送到」「排序方式」。
（这三项系统里有，但日常用不上，留着只占宽度。）

- **多选属性**：以前只弹第一个选中项的属性。现在多选时把选中的对象装进一个
  `IDataObject`（`SHParseDisplayName` 求 PIDL → `SHCreateDataObject`），
  再交给 `SHMultiFileProperties` 弹系统的「多个项目属性」窗口
  （顶部显示"N 个文件"、有"计算大小"、第二页能改公共属性）。
  PIDL 组不起来（选了虚拟项）时退回第一个的属性。
- **在新窗口中打开**：再启动一个自身进程，把目录当命令行参数传过去。
  `main.cpp` 新增 `ExtractStartupPath` 解析 `lpCmdLine`（去空白、去成对引号），
  `MainWindow::Create(hInstance, initialPath)` 接受初始目录；
  WM_CREATE 里"命令行目录可用就用它，否则按上次停的目录"。两个窗口互不影响。

### 空白处菜单的最终分组（用户定稿）

    查看 >
    刷新                                      ← 和「查看」同一组，紧在它下面
    ─────────
    粘贴                                      ← 剪贴板里有文件才出现
    撤销 删除 / 重命名 / 移动 / 复制 / 新建     ← 紧跟「粘贴」的下一格，有才出现
    恢复 删除 / 重命名 / 移动 / 复制            ← 撤销过才出现（「新建」不可恢复）
    ─────────
    新建文件夹
    新建 >
    ─────────
    属性

### 撤销 / 恢复（多级，Ctrl+Z / Ctrl+Y）

两个栈：`m_undoStack`（撤销栈）和 `m_redoStack`（重做栈），最多 50 级。
每一步记成一条 `UndoRecord`：操作前在哪（`beforePaths`）、操作后在哪（`afterPaths`）。

- 操作成功 → 压进撤销栈，并清空重做栈（和常见编辑器一样，有新动作就不能恢复旧的了）；
- Ctrl+Z / 右键「撤销」→ 从撤销栈弹一步，反着做，做完压进重做栈；
- Ctrl+Y → 从重做栈弹一步，按原方向再做一遍，做完压回撤销栈。

文案按栈顶那一步拼，跟系统一个字不差：「撤销 删除」「撤销 重命名」「撤销 移动」
「撤销 复制」「撤销 新建」；「恢复」同理。栈空时那一项整条不出现（不是变灰）。

**这组项在四种场景的菜单里都有**，位置一律是「剪切／复制／粘贴」那一格的下一格：

- 空白处：查看、刷新 ┃ 粘贴 ┃ 撤销、恢复 ┃ 新建 ┃ 属性
- 单选文件：打开、打开方式 ┃ 剪切、复制 ┃ 撤销、恢复 ┃ 删除 ┃ 重命名 ┃ 属性
- 单选文件夹：打开、在新窗口中打开 ┃ 剪切、复制 ┃ 撤销、恢复 ┃ 删除 ┃ 重命名 ┃ 属性
- 多选：打开 ┃ 剪切、复制 ┃ 撤销、恢复 ┃ 删除 ┃ 属性

盘符 / 此电脑这类命名空间项不带（那上面没有可撤销的文件操作）。

| 操作 | 撤销怎么做 | 恢复（Ctrl+Y）怎么做 |
| --- | --- | --- |
| 新建（文件夹 / 新建菜单里的文件） | 把刚建出来的那项删掉（进回收站） | 不支持（内容已进回收站，做不出同一个文件），同时清空重做栈 |
| 复制粘贴 | 把副本删掉 | 再从源复制一份 |
| 剪切粘贴（移动） | 从目标目录搬回原目录 | 再搬到原目标目录 |
| 重命名 | 改回原来的名字 | 再改成新名字 |
| 删除 | 从回收站还原 | 再删一次 |

记录什么时候写：
- 新建 / 重命名是同步操作，成功后立刻压栈；
- 复制 / 移动 / 删除走后台线程，在 `WM_APP_OPERATION_DONE` 里 **SUCCEEDED 时才压栈**
  （用户点取消、失败都不留记录，避免菜单上出现一个按不动的东西）。

删除的撤销：回收站里每一项都有 `System.Recycle.DeletedFrom` 属性（原来在哪个目录），
配合项名还原出完整原路径，匹配上就用 `IFileOperation::MoveItem` 搬回原目录。
这个属性键 SDK 的 `propkey.h` 里没有，运行时用 `PSGetPropertyKeyFromName` 按名字取。
回收站被清空过、或者找不到同名项时静默跳过（只刷新列表，不弹错误框）。

# 阶段 15：「此电脑」平铺分组铺满 + 容量单位统一（1024 进位）

## 15.1 平铺分组标题行填满

问题：窗口宽一点是 3 列、窄一点是 2 列，「设备和驱动器 / 网络位置」这行标题
只占 1 格，后面空着的格子会被下一张卡片占掉，标题右边就冒出卡片，整片错位。

做法（虚拟列表下没法手动定位，只能靠「插占位格 + 控件自动排列」）：

1. 标题后面补 `perRow - 1` 个占位格，把这一行剩下的格子填掉，标题独占一行；
2. 每组末尾如果没填满一行，也补齐，否则下一组标题会挤在半行上；
3. **perRow 必须是控件真实的一行格数**，不能写死「客户区宽度 / 300」：
   改成 `FileListView::TilesPerRow()`，问控件要 `LVM_GETITEMSPACING` 的列宽再除；
4. **窗口宽度一变列数就变**，所以加了 `MainWindow::RefreshThisPcGrouping()`：
   `WM_SIZE` 和 `ApplyViewMode` 末尾各调一次，算出新的 perRow 跟成员
   `m_thisPcPerRow` 比，只有不一样才把上一次插的标题/占位格剔掉、按新列数重建、
   再 `SetResult`（SetResult 内部会自己恢复选中项和滚动位置）。

分组本体抽成了文件级 `static void BuildThisPcGrouped(entries, perRow)`，
枚举完成和窗口重排都调它，保证两处排法完全一致。

实测（临时把配置里的 lastFolder 设成此电脑 + 平铺）：

- 窗口 1279 宽 → 日志「一行 3 格、总行数 13」，设备组 2 张卡 + 1 个占位格，网络组从新行开始；
- 拉到 1000 宽 → 日志「一行 2 格、总行数 10」，布局同样正确，标题行没有露出卡片。

## 15.2 容量单位统一 1024 进位

- 新增 `format::CapacityText(uint64_t)`：磁盘容量行专用，1024 进位自动升
  KB→MB→GB→TB→PB→EB，按 3 位有效数字（≥100 不带小数、≥10 一位、其余两位），
  不足 1 KB 显示「N 字节」。
- `format::SizeText` 扩到 B/KB/MB/GB/TB/PB/EB（原来只到 GB，超过 1024GB 会写成 1234.5 GB）。
- 「此电脑」卡片上的「X 可用，共 Y」改调 `CapacityText`。
  实测显示「1.22 TB」「12.7 TB」「838 GB」「7.96 GB」，不再出现 1025 GB 这种。

验证方式：编译 0 错误；临时切到「此电脑」平铺截 3 列 / 2 列两版对照；容量文本实测见上。

# 阶段 16：设置里「注册为默认文件管理器」

设置窗口加了第二个按钮，按注册表实际状态显示两种文案：
- 没注册：注册为默认文件管理器
- 已注册：恢复系统默认文件管理器

只接管「双击文件夹 / 双击磁盘」这一层动作：

| 注册表位置（全部在 HKCU，无需管理员） | 注册时写成 |
| --- | --- |
| `Software\Classes\Directory\shell`（默认值） | `open` |
| `Software\Classes\Directory\shell\open\command` | `"本程序全路径" "%1"` |
| `Software\Classes\Drive\shell`（默认值） | `open` |
| `Software\Classes\Drive\shell\open\command` | `"本程序全路径" "%1"` |

「默认动词」那两处是必须的，原因见踩坑记录第 27 条 —— 缺了它命令写了也不生效。

备份与恢复：
- 第一次注册时把 4 个原值（原来有没有 + 原来是什么）备份到
  `HKCU\Software\FileExplorer\DefaultFileManager`，之后再注册不覆盖备份，
  所以先注册 Debug 版、再注册 Release 版，也还能回到"第一次注册之前"的原状。
- 恢复时原样写回（保留原来的 REG_SZ / REG_EXPAND_SZ 类型，
  `%SystemRoot%\Explorer.exe` 这种才不会被展开坏）；
  原来没有的值就删掉，并把我们建的空壳键一层层收掉，最后连备份键一起删。
- 两个动作都调 `SHChangeNotify(SHCNE_ASSOCCHANGED)`，不用重启就生效。

不管的东西：Folder 类（桌面、控制面板、库）一个值都没动；Win+E、任务栏上的
「文件资源管理器」、运行框里输路径回车，仍然打开系统资源管理器。

实测记录（Debug 版，全部动真注册表，测完已恢复干净）：
- 点注册 → 四处值都写对；用 `Start-Process` 打开 owtest 文件夹，进程数 1→2，
  新进程带目录参数；打开 `C:\` 盘符进程数 2→3，说明 Drive 类也接管了。
- 点恢复 → HKCU 下两个 `shell` 键整棵消失、备份键消失，`HKCR\Directory\shell`
  回到 `none`，再打开文件夹不再启动本程序。
- Debug / Release 两个配置都编译通过。

# 阶段 18：命令行传进来的是"文件"时，打开所在目录并高亮它

## 问题

以前命令行参数一律当"要打开的目录"处理。别的程序（或系统"打开所在文件夹"
之类的调用）把**文件路径**传进来时，打不开、只能回退到默认目录。

## 现在的规则

## 1）地址栏的 ">" 换成自绘小箭头

关键点：GDI 的 `LineTo` 画的斜线没有抗锯齿（一格一格的毛刺），

- `Draw` 里用 `AlphaBlend` 把这张位图贴到两段中间（需要 `msimg32.lib`，

- 尺寸：基础是 Scale(3)（横向伸出）、Scale(5)（上下各伸出），再整体乘一个 zoom（当前 0.9，即缩到九成），

# 视图独立记忆：此电脑 / 控制面板（提交 8e11b40）

## 需求

- 全局（普通文件夹）那套视图逻辑完全不变：用户手选过就锁全局，没选过按目录类型给默认。
- 「此电脑」和「控制面板」（含「所有控制面板项」及其分类子页）从全局里摘出来，**各自单独记忆**。
- 这两处默认都是**平铺**；各自在右键「查看」里切换后互不影响，也不影响全局。

## 配置结构

`settings.json` 的 `view` 段多出一张「位置 → 视图」表：

```json
"view": {
  "manual": false,
  "mode": 3,
  "locations": {
    "thispc": 4,
    "controlpanel": 2
  }
}
```

- 键：`thispc` / `controlpanel`（固定英文，路径写法将来改了也不影响）。
- 值：`0` 大图标、`1` 小图标、`2` 列表、`3` 详细信息、`4` 平铺。
- 启动时读进内存 `std::map`，导航时只查内存：**零 IO、零 COM、零注册表**，右键菜单和切目录速度不受影响。

## 关键实现

- `Settings::LocationViewMode(key)` / `SetLocationViewMode(key, mode)`：只动内存，返回 -1 表示“没记过”。
- `MainWindow::ViewLocationKeyForPath(path)`：`此电脑` 按全名比较；控制面板按根路径
  `::{26EE0668-A00A-44D7-9371-BEB064C98683}` 前缀比较，所以子项和分类子页都算同一处。
- `MainWindow::DefaultViewModeForLocation(key)`：记过就用记的，没记过就是 `Tiles`。
- `OnEnumerationDone`：位置页永远按自己那份；普通目录没锁定按类型默认，锁定后若被位置页带跑则恢复全局那份。
- `ApplyViewMode`：用户手选时按当前位置决定写位置表还是锁全局（`m_globalViewMode` 记普通目录那份）。
- `SaveWindowState`：站在位置页关闭时只更新位置表，并用 `m_globalViewMode` 写全局，
  避免“位置页的视图被顺手写进全局”。

## 顺手修掉的既有 bug

列表视图下「此电脑」的分组标题「设备和驱动器」「网络位置」各出现两遍、真实项只显示 4 个（状态栏 6 个）。

修法：每次枚举完成都重建分组，`BuildThisPcGrouped` 自己先剔除旧标题和占位格（幂等）。

4. 普通目录（桌面）在 `manual=true`、`mode=2` 下 → 列表，不受位置记忆影响。通过。

# 同一目录不重复开窗口 + Ctrl+双击在新窗口打开

## 需求

1. 打开某个文件夹时，如果已经有一个窗口停在这个目录，把那个窗口拉到前台就行，别再开新窗口。
   （右键「在新窗口中打开」、Ctrl+双击 也按这条去重；只有没有任何窗口停在该目录时才真的开新窗口。）
2. 列表里按住 Ctrl 双击文件夹 = 在新窗口打开（和右键那个菜单项同一个效果）。
3. 外部启动带的是**文件**、而且父目录已经有窗口在显示时：把那个窗口拉起来并选中这个文件。

## 实现

新文件 `src/ui/WindowRelay.h/.cpp`：跨进程的「这个目录我开着了」接力。

- 类名 `FileExplorerMainWindow` 只留一个出处（`ui::kMainWindowClassName`），MainWnd.cpp 引用它。
- `RelayOpenFolderToExistingWindow(folder, selectFile, selfWindow)`：
  枚举同类名的可见顶层窗口 → 对每个发 `WM_COPYDATA`（`dwData = 'YEx1'`，请求体是定长数组，
  不能用指针，跨进程会失效）→ 对方比对当前目录（`IsSameFolder`：忽略大小写、去尾斜杠、`C:\` 这种根保留）→
  命中就 `ShowWindow(SW_RESTORE)` + `SetForegroundWindow` + `BringWindowToTop`，回 1；
  发送方收到 1 就不再开窗口。
- 前台权限：Windows 不允许后台进程抢前台，所以发送方先 `AllowSetForegroundWindow(对方PID)`，
  再用 `SendMessageTimeoutW(..., 2000ms)` 同步问一句（对方卡死也不会拖住调用方）。
- 三个入口统一走 `MainWindow::OpenFolderInNewWindow`：右键菜单、Ctrl+双击、以及 `main.cpp` 带路径启动前的那次检查。
- 带文件的情况：`ActivateFromRelay` 激活窗口后直接 `SelectPaths` + `EnsureVisiblePath`；
  列表还没枚举完就先存进 `m_startupSelectFile`，等 `OnEnumerationDone` 时再选（复用原有的"启动后选中文件"机制）。

Ctrl+双击：

- `FileListView` 的 `NM_DBLCLK` 改成用 `NMITEMACTIVATE::iItem`（鼠标命中的那一项），不再用"当前选中项"——
  按住 Ctrl 点第一下会把该项取消选中，用选中项取会什么都打不开；没有命中项时才回退到选中项。
- Ctrl 状态用 `GetAsyncKeyState(VK_CONTROL)`（读真实物理/注入键状态），不用 `GetKeyState`（跟着消息队列走，会读到旧值）。
- 回调签名改为 `void(size_t index, bool openInNewWindow)`；主窗口里只有文件夹才开新窗口，文件仍按默认程序打开。

成本：只在"要开新窗口"的那一刻做一次枚举 + 一条同步消息；日常导航和右键菜单完全不碰。

## 验证

- 带参数启动（同文件同目录）两次：实例数始终 1；日志「该目录已有窗口，本次启动交给它」+
  「收到其它窗口的请求，已选中文件」，截图确认窗口被拉到前台且 README.md 选中。
- 换一个目录启动（C:\git）：实例数变 2，正常开新窗口。

  （SetForegroundWindow 被系统拒绝，点击落到了列头上），这两处请手工确认。

- **预览与校验**：`BuildPreviewRows` 一次算好小写路径、原名、新名：
  目标名冲突用 `unordered_map` 查占名者，重名用计数表，整体 O(n)；
  校验项包括 >255 字符、只有点、结尾是空格或点、系统保留名（CON/PRN/AUX/NUL/COM1~9/LPT1~9）、
  与同批项重名、已存在同名文件、可能被占用、没有改名权限、文件已经不在了。
  异常行整行标红，状态列文案缩短（长文案会被列宽截成「…」）。
- **性能**：源状态探测在 `WM_TIMER` 里节流 800ms；去掉打开窗口时多余的 `Recalculate()`；
  下拉框边框刷子、等宽字体改静态缓存。
- **改名**：两段式（原名 → `~brex_<i>` 临时名 → 目标名）；第二阶段失败按两轮回滚
  （先倒序撤 `stage==2`，再倒序撤 `stage==1`），避免 a↔b 互换残留临时名；
  只把真正改过名的项作为结果回传，没改动的项不再产生「原文件名与目标名相同」的撤销记录。
- **撤销**：`UndoRecord` 加 `bool batchRename`；批量记录压入撤销栈，右键菜单照常可用；
  Ctrl+Z / Ctrl+Y 拆成键盘专用命令 `kCommandUndoKeyboard` / `kCommandRedoKeyboard`，
  栈顶是批量记录时键盘调用整条不执行（不跳过、不去撤更早一步），只在日志留一行提示。
  批量撤销/重做走 `RenameManyTwoStage`（直接用 `MoveFileExW`，不为每项起 COM 操作），
  并新增 `MakeLongPath` 支持 >260 字符路径。
- **健壮性**：`GetTextOf` 缓冲区改 `length+1` 再截断；模板数值字段统一 `ClampInt`（位数 1~20）；
  模板文件读写失败（`%APPDATA%\FileExplorer\rename_templates.txt`）返回 bool 并弹窗告知；
  字体只在 `m_ownedFonts` 为真时删除，不再误删 `DEFAULT_GUI_FONT`。

## 内存占用说明（调查结论，未改代码）

用户反馈「最近几轮改完后内存 10 多 M，之前不到 5M」。A/B 对照 `v1.1.2`（批量重命名之前的代码）
同条件 14.80MB / 专用工作集 10.61MB，与当前 Release（14.50 / 10.40）基本一致；
进程里 21 个线程有 12 个来自微信输入法注入的 `wetype_tip_core.dll`(9) 与 `wetype_tip.dll`(3)
（合计约 7.9MB 文件），未注入时是 10 线程 / 8.2MB。16 秒时间线平稳、开关批量重命名 ±0.02MB，
不存在泄漏。输入法注入是 TSF/IMM32 的标准机制，应用侧只有 `ImmDisableIME` 这种「连中文一起禁」
的手段，不可用；结论是保持现状。
